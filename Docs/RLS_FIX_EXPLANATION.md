# RLS Policy Type Mismatch - Root Cause & Solution

## 🔴 The Problem

### Error Message:
```
ERROR: operator does not exist: bigint = uuid
HINT: No operator matches the given name and argument types. You might need to add explicit type casts.
```

### Root Cause:
Your `user_profiles` table has TWO ID columns:
- `id` (bigint, identity) - Auto-incrementing integer primary key
- `user_id` (uuid) - References `auth.users.id` (the Supabase Auth user UUID)

The RLS policies were incorrectly comparing:
```sql
user_profiles.id = auth.uid()
     ↓                  ↓
   bigint              uuid  ❌ TYPE MISMATCH!
```

## ✅ The Solution

Compare against the **correct UUID column** (`user_id`):
```sql
user_profiles.user_id = auth.uid()
        ↓                    ↓
      uuid                 uuid  ✓ TYPES MATCH!
```

## 🚫 Why NOT Use Type Casting?

### You COULD cast like this:
```sql
WHERE user_profiles.id::text = auth.uid()::text
```

### But DON'T because:

1. **Performance Hit**: Casting prevents index usage, causing full table scans
2. **Code Smell**: Indicates wrong column being used
3. **Fragile**: Breaks if data types change
4. **Unnecessary**: The correct UUID column (`user_id`) already exists!

### The Right Fix:
Use the correct column that's already the right type:
```sql
WHERE user_profiles.user_id = auth.uid()  -- ✓ Clean, fast, correct
```

## 🗂️ Your Table Structure

### user_profiles table:
```sql
CREATE TABLE user_profiles (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,  -- Sequential ID
  user_id uuid REFERENCES auth.users(id),                  -- Auth user UUID ← USE THIS
  email text,
  role text,
  -- ... other columns
);
```

### Why Two IDs?
- `id` (bigint): Internal sequential primary key for relationships
- `user_id` (uuid): Links to Supabase Auth system

### When comparing with auth.uid():
Always use `user_id`, NEVER use `id`.
