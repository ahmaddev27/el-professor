- **Overlapping salary rows (PR #71), what to know:**
  - The owner decided on 17.09.2026 that he merges overlapping salary rows by hand before paying, and that `confirm_salary_cash_payment`'s `overlapping_salary` refusal stays. PR #71 makes them findable: an amber badge beside the driver's name on the Gehälter screen, naming each overlapping row's period and amount. No query is added — it is folded out of the rows the screen already loads, in one `useMemo`. `src/utils/salaryPeriodOverlap.ts` is the pure detection, 19 tests.
  - **How they are created, established before proposing to prevent them.** Exactly two paths write a `salaries` row, both a click on the Gehälter screen: `SalariesManagement.tsx:301` (mark paid/unpaid) and `SalaryDetailsModal.tsx:119` (`ensureSalaryExists`, which fires *automatically* when the payments dialog opens on a driver with no row for that period). Nothing else — no import, no planning run, no Abrechnung, no edge function, no trigger, no RPC. Every period the app itself computes is a **business month** (`getBusinessMonthRange`, whose calendar-month fallback is unreachable), and consecutive business months never overlap. The overlap comes from the two free-form date inputs at `SalariesManagement.tsx:449-475`, which write any pair of dates unvalidated, past a `unique_driver_period` that covers only `period_start`. **So overlaps are hand-entry, not a supported flow** — a guard in the write path would break nothing that exists today.
  - **There is no way to merge the rows in the product.** No screen deletes a `salaries` row and none edits `period_start`/`period_end`. "By hand" means a direct database edit. Whether the screen should grow a delete for a salary with no payments is a separate open question.
  - **Preventing new ones is proposed, not built**, and written up in PR #71's body for the owner: an application check at the two insert sites first, then a BEFORE INSERT (not UPDATE — merging needs edits) trigger, and **against** an exclusion constraint, which validates the whole table on `ADD CONSTRAINT` and so could not ship while any company still holds an overlap, raises on an inverted period, and would need a `SCHEMA_EPOCH` bump.
- **Button label contrast (PR #72), what to know:**
  - **The trap, because it will be walked into again.** `--accent` is the accent *background*; `--accent-text` is accent-coloured *text for a normal background*. The names read as a pair and are not one. In the light theme both hold `#2563eb`, so `background: var(--accent)` with `color: var(--accent-text)` painted the label in the button's own colour — **1.00:1, the text simply absent**; in the dark theme `#22d3ee` on `#06b6d4`, 1.34:1. The owner hit both on staging. The token for a label on a filled background is `--text-inverse`, which `.btn-primary` in `index.css` has always used and which was **the only pairing in the codebase that already passed**.
  - 73 label colours in 40 files now use it: `--accent-text` on `--accent` (9 sites, 1.00/1.34 → 5.17/7.31), white on `--accent` (58, 5.17/2.43 → 5.17/7.31), white on `--danger` (6, 4.83/3.76 → 4.83/4.71). **The light theme does not move** — `--text-inverse` is `#ffffff` there, which 58 of these sites already spelled literally; only the dark theme changes, and only from failing to passing. `--accent-text` keeps its 91 correct uses on neutral surfaces, four of which are now pinned as well.
  - **`--success` and `--warning` are the open half — 18 sites, and no token fixes them.** White reaches only 3.77:1 on `--success` and 3.19:1 on `--warning` in the light theme, and `--text-inverse` *is* white there, so it changes nothing: the background is too light for any legible label. Fixing it means darkening the two token values, which also moves every other use of them — both are already failing as text on their own `-subtle` fills (3.58:1 and 3.07:1), so darkening would fix that too. **That is a design decision for the owner, not a token swap.** The sites: `AdminSidebar.tsx:55`, `CarsManagement.tsx:242`, `FahrtenbuchImportModal.tsx:1398`, `IncomeManagement.tsx` ×2, `UserManagement.tsx:1180`, `WerkstattCheckModal.tsx:443`, `BargeldbestandPage.tsx:360`, `BelegePage.tsx:166`, `PlatformLoginPage.tsx:179`, `SuperAdminDashboard.tsx` ×4, `WerkstattPage.tsx` ×3.

Both carry the reasoning in a header comment so the next reader does not "fix" them; the second also self-checks that it can still see style objects, so a broken parser cannot pass by finding nothing.

A two-line grep window reported ~7 defects; a 14-line window found 12 candidates of which **3 were false positives** (the importer's step bar carries no text, its label sits on the modal background; the OTP resend link's `--accent-text` branch has no background). Every hit was read in source before being changed. Disabled branches were left alone on purpose — `--text-tertiary` on `--bg-muted` is 2.24:1, but WCAG 1.4.3 exempts inactive controls and "fixing" it makes disabled buttons look enabled.

- **Bargeldbestand on the cash ledger (PR #43, plan 4.3b), what to know:**
  - `BargeldbestandPage` and the Overview cash panel read `cash_movements` through `utils/cashLedger.ts`. Both establish scope before making any claim: `cash_movements` and `salary_cash_receipts` are readable by the owning company only, so platform staff inside a customer read that customer's Bargeld and Belege and none of its movements. An empty set there is indistinguishable from "no payouts", so out of scope the payout card is dropped, the older "Bargeld − Belege" label kept, and the caveat carried into the Excel dump. Printing 0,00 € would have turned a missing read into a false claim.
  - Five defects from the review, all fixed before merge: a literal minus prefixed to an already-signed number (a receipt paid in one month and voided in the next rendered "−-300,00 €"); none of the three queries paginated, and the largest staging company already holds 836 receipts against PostgREST's silent 1000-row cap, so the balance would have under-reported cash with no failure signal; `calcCashSummary` had no test; an unknown `source_type` made real cash vanish from the balance rather than merely be miscategorised; and the two new cards rendered a decimal point instead of the German comma.
  - **What the merge gate proved and what it did not.** Staging holds zero cash movements, zero receipts and zero Gehaltsquittung payments across 19 companies, so every comparison in the parity script had a third term of exactly zero: it proved the two formulas equivalent and never exercised the divergence.
  - **The seeded check that does exercise it has now run on staging**, inside a transaction that ended in `ROLLBACK`, acting as the e2e test company's own admin under RLS rather than as a superuser: a driver, a salary of 300,00 € for March 2026, `confirm_salary_cash_payment` for 300,00 € dated 15.03.2026, then `void_salary_cash_receipt`. The payment produced receipt `GQ-2026-0001` and exactly one outgoing movement of 300,00 € in 2026-03; the void marked the receipt `voided` and produced one incoming movement of 300,00 € in 2026-09 — today's month, because a storno is booked on the day of the void. Net per month: 2026-03 is −300,00 €, 2026-09 is +300,00 €. The documented cash-book rule therefore holds against the live RPCs, not only in theory.
  - **Its limit:** that verified the database side — the RPCs write the movements with the right month attribution. It did not verify the screen, which rests on the four `calcCashSummary` tests PR #43 added, covering the same month boundary and the void landing in the next month. Nothing was left behind on staging, so a check against the rendered Bargeldbestand figures would still need data seeded and kept.
- **A cash salary payment is now a Gehaltsquittung (PR #69, plan 4.3d), what to know:**
  - **The defect it fixes is a ledger one, not a missing button.** `SalaryDetailsModal` inserted into `salary_payments` directly, so a payment added with `payment_type: 'cash'` wrote **no `cash_movements` row** — the money left the till and the Bargeldbestand did not move. The three Gehaltsquittung RPCs are the only writers of that ledger. The row also had no receipt, so `paymentRowActions` (which keys on `source_type = 'gehaltsquittung'`) had nothing to hang PR #49's preview button on. Adding a cash payment now hands the salary, the amount and the date to the existing `GehaltsquittungModal`, preselected and opening on its **amount** step, where the balance and the *Ort der Zahlung* are; the confirmation writes all three rows in one transaction and the lock, the badge and the preview appear on the new row by themselves.
  - **The existing dialog is opened, not copied.** `useGehaltsquittungFlow` holds the request id kept until the database answers, its resume out of `sessionStorage` after a reload, the pre-send balance re-read, and the `overlapping_salary` / `overpayment` / `request_id_conflict` refusals. A second client for `confirm_salary_cash_payment` would have to keep all of that identical, and the failure mode of drift is a payment booked twice. The one new option is `preselect`; **an unanswered confirmation still wins over it**, because that one may already be booked.
  - **The rule is keyed on the origin of the write, never on `payment_type` alone**, and that is the part not to touch. The weekly "Bar zurück" (`weekly_cash_difference`) is also stored as cash, and CLAUDE.md is explicit that it counts as paid and never moves cash — a rule of "type is cash → receipt" would book a payout from a till that was never opened. `src/utils/salaryPaymentWrite.ts` is that decision, pure and tested without a database; `handleWeeklyCashPayment` asks it too and throws if it ever answers anything but `insert`.
  - **A stored cash row is frozen in its amount and its payment type**, and the form disables both fields rather than refusing on submit. The review of this PR found the hole: `paymentRowActions` gives the pencil to every non-`gehaltsquittung` row, so a legacy cash payment of 100,00 € could be edited to 5.000,00 € — 4.900,00 € more asserted as paid in cash with no ledger row anywhere, the same defect through a different door, reachable on any legacy row by anyone with salaries-edit. Date and description carry no cash claim and stay editable. The way to correct such a row is to delete it and record it again, which now creates the receipt and moves the till, and the message says exactly that (`sal.payment.cashRowLocked`) — there is nothing to void, because the row predates receipts.
  - **Nothing is backfilled, and what that leaves standing is worth stating plainly: every cash payment recorded before 17.09.2026 still asserts money that left the till with no `cash_movements` row behind it, and no migration corrects them.** The Bargeldbestand of any company that recorded cash salary payments before this release is therefore high by the sum of those rows, permanently. They keep their row and their delete button; they get no retroactive receipt. The other door into an untracked cash payment — create it as a bank transfer, then edit its type to cash — was open before this PR and is now refused by name (`sal.payment.cashNeedsReceipt`), because `confirm_salary_cash_payment` writes its own row and cannot adopt one.
  - **A salary whose period overlaps another row of the same driver can now take no cash payment at all, and that is a deliberate capability regression.** Before this PR such a payment was a plain INSERT and succeeded; now it is a Gehaltsquittung, and `confirm_salary_cash_payment` refuses an overlapping salary (`overlapping_salary`). **The owner decided on 17.09.2026 that the refusal stays**: he merges the two rows by hand before paying, and the system keeps refusing until he has. A bank transfer is unaffected.

## Gotchas learned the hard way

- **ridy is off limits.** Its deploys reset its Caddyfile. The guard restored our section on both of ridy's deploys on 14.09.2026 (10:57 and 11:11 CEST).
- **`gh pr merge --delete-branch` switches the local checkout to the local base branch,** which may be stale. Pull right after.
- **`workflow_dispatch` workflows only become runnable once the file is on the default branch** (`main`).
- **Quoting through `ssh '…'` turns `$[` into bash arithmetic expansion.** Send scripts with `ssh host bash -s <<'EOF'` instead.
- **Caddy accepts any `@name` as a named matcher,** so a template placeholder must be an invalid directive to fail closed.
- **The `Enter passphrase for key … id_ed25519` prompt is local to your machine.** Pressing Enter falls back to the server password.
- **GoTrue v2.170.0 only rate-limits when `GOTRUE_RATE_LIMIT_HEADER` is set;** otherwise it silently does nothing.
- **Playwright applies the config's `httpCredentials` to every request context, including `request.newContext()`.** A "visitor without a login" built that way silently sends the test login. Use Node's `fetch` for anonymous checks.
- **supabase-js strips the URL hash while it creates a session from a link.** Anything that needs `type=` or `error=` must read it before the client is created; see `authRedirect` in `src/lib/supabase.ts`.
- **A single-file bind mount whose file is missing becomes an empty directory.** Mailpit then cannot read `mailpit-relay.yml` and does not start, or starts without its UI login. `deploy.sh` checks both files before a staging release.
- **"No buffer space available" / `ERR_NO_BUFFER_SPACE` on the dev machine means it ran out of sockets,** not that the host is down. On 14.09.2026 the MyPublicWiFi service held 16,000 bound sockets, and e2e, git and ssh all failed until it let them go. It came back the same day, and six agents died after five hours with `ENOTFOUND`. Stopping the service is the only real fix.
- **Mailpit logs a relay only when it fails;** success is a debug line, so a quiet log is the good case. To see what Resend did with a mail, list `GET https://api.resend.com/emails` with production's key (pass the header on stdin with `curl -H @-`) and read `last_event`. Print only the fields you need: the list holds customers' addresses.
- **A `grep` that matches nothing ends a `set -euo pipefail` script silently** — the same trap as the `.env` reads in `deploy.sh`. It hid the result of the first relay test, which had in fact been delivered.
- **On Windows, vitest rewrites the golden `.snap` files with LF line endings.** The content is byte-identical and `git diff` is empty, but with `core.autocrlf=true` git lists them as modified. Restore them with `git checkout -- src/utils/__snapshots__/` and never commit them. A `.gitattributes` line `src/utils/__snapshots__/*.snap text eol=lf` would end the churn.
- **A release copies only part of `deploy/`.** `install_release` copies the compose file, `kong.yml`, `nginx-spa.conf`, `deploy.sh`, `init-db`, the functions, the migrations and `dist`. Any other script the host runs (`set-*.sh`, `otp-housekeeping.sh`) stays at the copy installed by hand, so reinstall it when it changes.
- **Supabase grants EXECUTE on every new function to PUBLIC, anon and authenticated.** A function meant for service_role only needs all three revoked; `20260911120000` missed anon. A guard written as `auth.email() != '…'` or `auth.uid() <> …` lets an anonymous caller through, because the comparison is NULL. For every SECURITY DEFINER function a PR adds, check `has_function_privilege('anon', …)`.
- **Never delete a PR's branch before `gh pr view N --json state` says MERGED.** On 15.09.2026 a merge failed on a GitHub TLS timeout, the script deleted the branch anyway, and GitHub closed PR #11 unmerged. Pushing the head commit back and `gh pr reopen` recovered it.
- **An inline `style` beats a Tailwind class.** Most screens set their layout in `style={{…}}`, which cannot change with the screen width. A class such as `hidden md:flex` next to an inline `display` hides nothing. On 15.09.2026 that kept the landing page two to four columns wide on phones. Anything that has to follow the viewport (grid columns, padding, display) belongs in classes, not in the style object.
- **The Workflow tool does not save an agent's worktree.** When a run is cut off, commit what is on disk (as `wip:`) before relaunching; a resumed run only replays agents that had finished.
- **Nothing creates a `user_profiles` row by trigger.** `auth.users` carries only `mark_pending_oauth_signup` and `sync_user_profile_email`; `public.handle_new_user` exists and nothing invokes it. Every profile is written by a signup RPC. Any code or test that assumes a profile appears on its own is wrong — and `tests/rls/oauth-signup.sql` creates that trigger in its own prelude, so the RLS kit cannot catch the assumption.
- **Production's compose reads the GoTrue signup switch as `DISABLE_SIGNUP`, not `GOTRUE_DISABLE_SIGNUP`.** Setting the prefixed name there changes nothing and reads as if it had.
- **A platform account cannot be hard-deleted once it has issued activation codes.** The delete fails with `23503` on `activation_codes_created_by_fkey`, and forcing it would destroy real history. Disable the staff row instead; that is what was done to `admin@yamobility.de` on staging.
- **`otp-request` answers 202 for the public purposes whatever happened**, including when the address has spent its five codes for the hour. That is deliberate — the endpoint must not reveal whether an address has an account — but it means "the mail never arrived" and "we refused to send it" look identical from outside. When a code does not turn up, count the hour's sends in `app_private.otp_send_events` before suspecting the mailer.
- **A local resolver that refuses a name is not a missing DNS record.** On the dev machine `nslookup mail-staging.elprofessor.eu` answered `Query refused` from a local resolver while the record was perfectly fine — it resolves through `1.1.1.1` and the site answers. Same family as the MyPublicWiFi socket problem below: check against a public resolver, or with `curl -w '%{remote_ip}'`, before reporting DNS as missing.
- **The platform panel moved to `/admin`.** `/super-admin/*` is a rewrite, not a second route table, and the in-app links still point at the old path on purpose. Slice 3.13 removes the rewrite and those links **together**.
