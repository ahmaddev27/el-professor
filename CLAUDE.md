# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Keep this file at the repository root — Claude Code only auto-loads `CLAUDE.md` from the project root or `.claude/`. A copy under `Docs/` is not loaded and will silently drift.

## Project

**El-Professor** — a multi-tenant, German-language SaaS for German taxi & Mietwagen fleet operators. A React SPA talking directly to Supabase (PostgreSQL + Auth + Storage + Edge Functions). There is no application server of our own.

Y&A Mobility is one customer company, not the product. Text that names the product says El-Professor. The `ya-mobility` in the compose project, volume, container and backup names predates that and stays, because production's data lives in those volumes (see `PROJECT_NAME` below). The `@yamobility.de` addresses in code and SQL are real accounts and stay too.

The domain is German payroll & compliance paperwork: import the monthly Fahrtenbuch (XLSX ride log), assign drivers to vehicle blocks, produce Stundennachweise (statutory time records) and a corrected Fahrtenbuch that reconcile with the Steuerberater's payroll figures.

Numbers use German formatting (decimal comma: `41,47`), dates `DD.MM.YYYY` in the UI and `YYYY-MM-DD` in storage. **Never use US `MM/DD/YYYY`.**

### Language

The UI is bilingual German/English; German is the source language and the fallback. `src/i18n/de.ts` is canonical and defines the key type, `en.ts` is a `Partial`, so screens convert incrementally and a missing English key renders German rather than a raw key. `useTranslation()` from `src/contexts/LanguageContext.tsx` gives you `t(key, vars)` and `tPlural({one, other}, count)`.

**The screens are converted.** The last visible German — labels, buttons, tooltips, placeholders, aria-labels and empty states — went through `t(...)` on 23.09.2026, alongside PR #112's engine keys. Adding a key still means adding it to **both** dictionaries; `scripts/i18n-merge.mjs` does that from a `{ "key": { "de": …, "en": … } }` file and refuses a placeholder that appears in one language only, a key already in `de.ts` with different text, or a collision between two agents.

What remains German is not leftovers but the three closed lists below, plus **anything a second consumer reads**. That last test is the one that catches people: a string is an identifier, not a label, when something compares, stores, exports or matches on it. Left German for that reason, each with a comment at its site: `wageLabel` in `HistoricalReconciliationWizard` (drawn into the Stundennachweis PDF); `MONTH_NAMES` / `MONTHS_DE` in Abrechnung, Dokumente and `InvoiceDetailModal` (date formatting, and the Abrechnung copy also builds the exported image's filename); `Woche N` in `IncomeManagement` (written into `income.description` and matched back with a regex); `ReceiptModal`'s category values and the `'Unsicher'` OCR prefixes; `SalaryDetailsModal`'s `description` and `payment_category`; `'Deutschland'` as a stored default; and the fallback sentences in `platformRpc.ts`, `platformStaffClient.ts` and `supportSessionClient.ts`, because the sentence a user actually sees on a refusal is `result.error`, written by the database in German.

**A chart series name is both a label and a key, and translating one half empties the chart.** Recharts matches `<Area dataKey>` against the property name on each datum, so a translated `dataKey` over German-keyed data resolves to nothing and the chart draws empty with no error — which is exactly what the Overview's 6-month trend and driver-performance charts did in English until 23.09.2026. Both sides come from the same `t(...)` call now, with `TREND_SERIES` in `overviewHelpers.ts` naming the trend series once. This is deliberately *not* the engine-message shape below: a series name has no second life, so it is a plain `t(...)`, not a German string carrying a key.

Three things stay German in both languages, and the reasoning is in the header of `src/i18n/index.ts`:

- **Generated documents.** Stundennachweis PDFs and the Fahrtenbuch XLSX carry statutory German text, and the `'original'` export mode has to reproduce the imported sheet's headers byte for byte. Translating any of it breaks the export and produces invalid records. Those strings live in the export modules, never in the dictionaries. The list is closed — the Stundennachweis PDF, the Fahrtenbuch XLSX, the Trinkgeld-Quittung, the Gehaltsquittung, the Mietwagenauftrag, and the two legal pages, the Impressum and the Datenschutzerklärung (their labels live in `src/lib/legalPages.ts`; the English UI says in one line that they are German). An `exportTableToExcel(...)` dump of vehicles, drivers, users, Fixkosten, the Bargeldbestand or Werkstatt checks is **not** on it: no statutory form, so its headers follow the UI language like any other label.
- **Domain vocabulary** — `Stundennachweis`, `Fahrtenbuch`, `Abrechnung`, `Beleg`, `Werkstatt`, `Monatsplanung`, `Lohnart`, `Bundesland`, `Gehaltsquittung` — so the screen and the paperwork agree.
- **Money and date formatting**, because on-screen figures map one-to-one onto German documents.

**The engines carry a key beside their text, they never call `t(...)`.** The pure modules under `src/utils/` — Phase 1/3/4, the repair pass, the clean engine, the trip analysis — are golden-mastered, feed exports and audit rows, and must not depend on the UI language. So a message keeps its German text and gains a `messageKey` (and `messageVars`) beside it, or `<field>Key` / `<field>Vars` where an object carries several messages; the screen renders `engineText(t, text, key, vars)` from `src/i18n/engineMessage.ts`, which falls back to that German whenever the key is missing from the dictionaries. Three rules:

- **A German dictionary entry must render exactly the text the engine already produced**, or turning a key on silently rewords the German UI. That is why `engine.phase3.repair.noValidMove*` is English in `de.ts`: that is what the planner writes today.
- **A var whose value is itself a key is translated first** (`engineText` does it), which is how a closed vocabulary — a note type, a conflict kind — travels inside a sentence without the engine reaching the dictionaries. A joined list cannot: `budget_not_computable` passes the German list and `budgetProblemKey()` exists for a screen that wants to rebuild it.
- **A German string that is a discriminator stays untouched** and gets no key: `warningCategories.classify()` sorts warnings by matching German fragments, `evaluateManualCandidate`'s `blockingChecks` are matched by `BLOCKING_CHECK_LABEL`, and `manual_exception.reason` / `assignment_reason` are persisted to `monthly_planning_manual_exceptions` — audit data, untranslated like `COMPANY_WRITE_SESSION_REASONS`.

Keys live under `engine.` in both dictionaries; `src/i18n/engineMessages.test.ts` reads the engines' source and fails the build when one is missing from either, including the families an engine builds from a code (`engine.noteType.${type}`).

### Golden-master tests

Coverage is narrow and deliberate: `src/utils/*.golden.test.ts` characterizes the money and calendar paths — `computeLohnartSeconds`, both German holiday tables, the business-week rule, and the amount in words printed on a Quittung (`germanAmountInWords`). They run in the build gate.

These are **characterization tests, not specifications.** They assert what the code does today so that Phase 3 changes become visible: correct a premium against §3b EStG and the affected snapshots fail, to be reviewed on purpose rather than discovered on a payslip. Do not "fix" a failing snapshot by regenerating it without reading the diff.

Two things they already pin down:

- The two holiday tables disagree every year, and the difference is always Easter Sunday: `getGermanNationalHolidays` (clean engine) counts Ostersonntag as a nationwide holiday, `getHolidaysForYear` does not. Ostersonntag is not a statutory holiday in Germany outside Brandenburg, so the clean engine grants a Feiertagszuschlag that is not owed — and since it is also a Sunday, the cumulation described in FINDINGS.md H19 compounds it.
- **`weekCalculations` is 0-indexed throughout.** January is `0`; `getBusinessMonthRange(4, 2026)` returns the range of **May**. Nothing else in the codebase says so, and a caller passing a 1-indexed month silently reads the wrong month.

`vitest.config.ts` pins `TZ=Europe/Berlin`. The payroll code walks local calendar days, so night, Sunday and holiday classification is timezone-dependent and the snapshots only mean anything in the product's own zone.

The same run tests the edge functions' pure modules: `vitest.config.ts` also includes `supabase/functions/_shared/**/*.test.ts`. Those modules (`otp-core.ts`, `smtp-core.ts`, `email-layout.mjs`, `otp-mail.ts`, `mail-template.ts`, `platform-access.ts`, `manage-users-routes.ts`, `notification-core.ts`, `notification-mail.ts`) import nothing from Deno, `npm:` or `jsr:`; keep it that way, or Node cannot load them. Their Deno halves — `activation-code-delivery.ts`, `notification-delivery.ts` — do, and have no test file for that reason. The Deno glue around them is checked with `deno check` in a throwaway `denoland/deno` container.

Component-embedded logic — the premium models inside `FinalizePlanningModal` and `MonatsplanungStundennachweisPreview` — is **not** covered, because testing it requires extracting it, and extraction is the sort of refactor these tests exist to make safe. Cover it after Phase 3 establishes what the numbers should be.

### The RLS kit and the permission matrix

`npm run test:rls` (`scripts/rls-test.mjs`; how to run it on the VPS is under *`app_private`* below) builds a throwaway database from production's `--schema-only` fixture with `CREATE SCHEMA public` softened to `IF NOT EXISTS`, `tests/fixtures/storage-shim.sql`, every migration from `20260908` on in filename order, `tests/rls/roles-seed.sql` and `tests/rls/seed.sql`. It then runs `tests/rls/assertions.sql` and every other file in `tests/rls` once, in name order. The same steps work by hand in `docker run --rm --network none --cpus 1 --memory 1g supabase/postgres:17.6.1.170` where node is not available, with the files in a `mktemp -d` directory under `/root` that is deleted afterwards, never against a running stack's database. Two of the files describe the boundary as a whole:

- `tests/rls/assertions.sql` — rules the boundary must keep.
- `tests/rls/matrix.sql` — phase 3's starting point. Seven principals (anon, viewer, editor, supervisor, company admin, an admin of another company, a platform owner with a `platform_staff` row) × every public table and view × SELECT/INSERT/UPDATE/DELETE/move. The UPDATE probe changes nothing, so it only reaches a policy's `USING` clause. The move (`M`) points a row at the other company, directly or through the parent that gives it its company, so it is the probe that reaches `WITH CHECK`, the clause phases 3.3 and 3.4 rewrite. It takes the row with `SELECT … FOR UPDATE` and moves it with `UPDATE … WHERE CURRENT OF`, because an UPDATE whose `WHERE` reads a column also has to leave the new row visible to the SELECT policies, and a tenant-scoped SELECT policy would hide a `WITH CHECK` that lets the row go anywhere. Each cell has two characters, one for a company-A row and one for a company-B row. An RPC section gives one character per principal to every SECURITY DEFINER function a client can call, and to the Abrechnung RPCs. Named scenarios cover the known holes, the profile privilege guard, and company and user state. Every table and view probe also runs as the owner and must succeed, so a refusal is never a malformed statement in disguise. The one exception is moving a trip, which the immutability trigger refuses even for the owner.

- `tests/rls/tenant-state.sql` — plan 3.3's own file. Ten companies, one per state the CHECK constraints allow (twelve until `20260919150000` retired `approval_status = 'suspended'` and `subscription_status = 'suspended'`), and four account statuses, each with a driver, an import and a trip: `get_active_company_id()` answers for the two controls App.tsx admits (a trial company, an invited employee) and NULL for every state it refuses, the business tables and the planning RPCs follow it, the account shell stays readable so the page explaining the block can render, and platform staff read a company's data but write none of it. It also states the shape as a rule — no policy reads `is_user_super_admin()`, no business policy reads `user_profiles`, `fahrtenbuch_trips` has no UPDATE policy — so a table added later that copies one of the old shapes fails here.

- `tests/rls/permission-coverage.sql` — slice C's own file (23.09.2026). For every table the permission system newly reaches, a role that may and a role that may not, on a read and on all three writes; the Fahrtenbuch by hand, because its commands are not uniform and its two `auth.uid()` INSERT clauses are what a restatement loses; the five planning RPCs with both refused roles and an administrator as the control; and the shape of the eleven objects that were already gated, so a release that loses one of those gates fails even if it never touched slice C. Whether a role *may* is read out of `role_permissions` rather than written down, so the probe and the seed cannot drift — section 6 is what pins the seed.

Like the golden masters, the matrix records **today's** behaviour, holes included. Each hole is tagged `HOLE[3.x]` with the plan step meant to change it. A migration that moves a cell fails the run and prints the expected and actual lines. Change the expectation in the same commit and name the change in the PR; never paste the actual line over without reading why it moved. A new public table or view, or a new SECURITY DEFINER function, is reported as `UNCOVERED`. That is a warning, not a failure, so parallel branches do not break each other's runs. Add its lines anyway.

The matrix does not probe `storage.objects` or edge functions, and it cannot see EXECUTE grants revoked before `20260908`. The storage shim gives a migration's bucket and policies something to apply to, but the fixture (`--schema=public`) carries none of the older storage policies. `tests/rls/storage.sql` probes storage instead: `20260920100000` restated the four company buckets' fifteen policies from a read-only capture of production (19.09.2026), so that file tests them, and `salary-receipts` as 3.3 left it, per principal, per kind of session and in storage-api's claim shape. `document-templates` is the one bucket with policies still outside the kit. The fixture carries no privileges either, so an RPC cell is `-` and not probed where a migration older than the fixture revoked that caller's EXECUTE and no newer one restated it. Every other anon cell assumes Supabase's default privileges, which grant anon EXECUTE explicitly when a function is created, so a `REVOKE … FROM PUBLIC` alone leaves anon able to call it (see *Known defects*).

`npm run test:rls` prints the notices and warnings psql writes to stderr, so UNCOVERED lines show up on a passing run too.

### The typecheck ratchet

`npm run build` used to be `vite build` alone. Vite strips types without checking them, so the project accumulated **376 TypeScript errors** that nothing ever surfaced — including undefined identifiers that threw at render, permission checks that were always true, four `ConfirmationModal` call sites using invented prop names (one dialog never rendered at all), and 71 `showToast` calls with their arguments reversed, which made every one of those notifications display the bare word "success" instead of its German message.

`scripts/typecheck-ratchet.mjs` now runs before every build and compares the error count against `typecheck-baseline.json`:

- **more** errors than the baseline → build fails, listing the worst files
- **fewer** errors → build fails, asking you to run `npm run typecheck:update` and commit the lowered baseline
- **equal** → build proceeds

Failing on improvement is deliberate: a baseline that moves only by an explicit commit stays honest. Use `npm run build:novalidate` if you genuinely need the bundle without the gate.

The remaining errors are not uniform. Roughly 182 are unused locals (`TS6133`, noise from `noUnusedLocals`); the rest include real type mismatches worth triaging. `TS2304` (undefined name), `TS2774` (condition always true) and `TS2367` (impossible comparison) are almost always genuine defects.

Env (`.env`, see `.env.example`): `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` are required; `VITE_APP_URL` is the origin baked into auth email redirect links (`/auth/callback`) and must be the real domain in production, or reset emails point at localhost.

## Environments and deployment

Two full, separate stacks run on one VPS (159.195.205.30), behind ridy's Caddy.

| | production | staging |
|---|---|---|
| web | `https://elprofessor.eu` | `https://app.elprofessor.eu` |
| API | `https://api.elprofessor.eu` | `https://api-staging.elprofessor.eu` |
| branch | `main` | `staging` |
| host dir | `/srv/PRO` | `/srv/PRO-staging` |
| compose project | `ya-mobility` | `ya-mobility-staging` |
| mail | Resend | Mailpit keeps a copy and relays to Resend — real recipients get it, `@example.com` never; read it at `https://mail-staging.elprofessor.eu` (login) |
| deploys | **Actions → Deploy → Run workflow** on `main`, confirm `production` | every push to `staging` |

- **ridy is off limits.** It is a separate live product that only shares the host: no commits to its repository, no stopping, restarting or recreating its containers. Solve El-Professor's problems on El-Professor's side.
- **Routing is `deploy/caddy/elprofessor.caddy`, and ridy's deploy erases it.** ridy's Caddy owns ports 80 and 443, so our site blocks are a marked section at the end of ridy's Caddyfile (`/root/ridy/docker/Caddyfile`). That file is tracked in ridy's git, and every ridy release runs `git reset --hard` and recreates its Caddy, which drops the section and takes both our stacks offline. `el-professor-caddy-guard` (`deploy/caddy/guard.sh`, run by a systemd path unit on every change to that file plus a one-minute timer) puts it back within seconds — measured at 7 s with no failed request. It validates the whole file in a throwaway container of ridy's own Caddy image before writing, only appends or replaces the text between its markers, writes in place because ridy's container bind-mounts the file by inode, and never restarts a container. Change routes by editing the repo copy and running `deploy/caddy/publish.sh`, which goes through the guard, checks all sites and ridy afterwards, and rolls back on failure. Never edit the section in ridy's file by hand. The guard and its units are installed on the host by hand, like the release wrapper — CI cannot change routing on a host another project depends on.

- **Never change production's `PROJECT_NAME`.** It prefixes the named volumes that hold production's data (`ya-mobility_db-data`, `ya-mobility_storage-data`); any other name makes Docker create empty ones and the site looks wiped. The compose file has no default for it on purpose, so a staging checkout that forgot to set it fails instead of mounting production's database.
- **Staging runs on a copy of production data**, real accounts and password hashes included. It shows a "STAGING" banner on every screen (`VITE_DEPLOY_ENV`), and its JWT secret, anon and service keys all differ from production's — a key from one environment is rejected by the other in both directions.
- **Staging mail reaches real people.** The owner decided on 14.09.2026, knowing staging holds real customers' addresses, that its mail is delivered the way production's is. GoTrue and the functions still send only to Mailpit, which keeps every message (the e2e suite reads links and codes there) and relays all of it through production's Resend account, except mail to `@example.com`. A password reset requested on staging for a real customer therefore reaches that customer, with a staging link. Test with `@example.com` addresses, and remember that staging now spends production's sending quota and reputation. `deploy/set-staging-mail-relay.sh` writes the relay settings on the host (`--test` sends one mail to Resend's sink, `--off` keeps mail on the host again); `deploy.sh` refuses a staging release without the settings file, or with relaying on and no `example.com` block. Verified 14.09.2026: Resend lists the relayed test mails as `delivered`. Mailpit logs a relay only when it fails, so its log stays quiet when mail goes out.
- **Merging to `main` deploys nothing.** The account's GitHub plan has no required reviewers or branch protection for a private repo, so the production deploy is a manual button. That job asks the host what staging is running (`status staging`) and refuses unless `main`'s git tree is exactly that release's tree — so an untested merge, a failed staging release or a staging rollback cannot be promoted.
- **CI can release, roll back and ask — nothing else.** The deploy key is bound in `authorized_keys` to `/usr/local/sbin/el-professor-release` (`deploy/ci-release.sh`) with `restrict`: no shell, no pty, no port forwarding, and only `release <env> <sha>`, `rollback <env>` and `status <env>`. The wrapper lives outside `/srv/PRO*` so a release cannot overwrite it, and it refuses any archive containing an `.env`. It is installed by hand; after changing `deploy/ci-release.sh`, reinstall it before merging, and keep it accepting what the currently merged workflow sends.
- **Every release is kept, and Actions → Rollback undoes one.** Each release lives in `/srv/PRO*/releases/<utc>-<sha7>/` with a `manifest.env` (sha, schema epoch, migrations applied, status); `releases/current` points at the live one, and the live release plus the five newest clean ones are kept. A rollback re-activates the newest earlier clean release through `deploy.sh --activate`: code, edge functions, Kong and nginx config go back, **the database does not**. That is only safe because migrations stay backward compatible with the previous release. A migration that cannot (a drop, a rename, a changed meaning) must bump `deploy/SCHEMA_EPOCH` in the same commit; rollback refuses to cross an epoch, and also refuses when the old compose file would change the `db` service or the auth settings (signup, login limits, the identity-provider switches and the auth entrypoint), or when the old release's `KONG_PLUGINS` or `auth-v1-closed` block in `kong.yml` differs. So no rollback crosses the release that brought Google sign-in's deploy settings; that is intended. **The epoch is 2 since `20260917130000`** (plan 3.3): that migration rewrote every tenant policy and moved company and user state into the database, and the release before it assumes both a staff account that may write any tenant's rows and screens that are the only thing keeping a suspended company out. The way back across it is the `pg_dump` snapshot `deploy.sh` takes before the migration runs, not a rollback. Undo a rollback by running Deploy again.
- **`deploy/deploy.sh` is the release.** Guards first (directory, project name, shared JWT secret, SMTP host, compose profiles, an `OTP_PEPPER` of at least 32 characters that staging does not share with production, the Google sign-in switch and client, Kong's `auth-v1-closed` block, the sign-in settings as compose renders them, and `kong.yml` run through `kong config parse` in a throwaway, network-less copy of the compose kong service, so a file Kong would reject is refused before the live gateway is recreated with it), then migrations, then Kong alone with a probe that its closed routes answer 403, then the bundle swap and the rest of the stack, then health checks. Migrations are tracked in `app_meta.schema_migrations` — a schema PostgREST does not expose — and each file runs in one transaction with its ledger row. An empty ledger on a populated database is refused; seeding it is `deploy.sh <env> --baseline`, typed once by a person. Production is snapshotted with `pg_dump` before any migration runs; the ten newest snapshots are kept. Health means the new bundle is live: CI writes the commit into `dist/version.txt`, and deploy.sh reads it back through the public URL; GoTrue's `/auth/v1/settings` must match the Google switch, and the closed routes must answer 403 through Caddy as well. deploy.sh needs `python3` on the host, as the release wrapper already did. `kong.yml` and `nginx-spa.conf` are single-file bind mounts their services read once at start, so their hashes are compose labels — an edited file recreates exactly its container.
- **Login attempts are limited per client.** GoTrue applies its limits on `/token` (password login and refresh), `/verify` and `/recover` only when `GOTRUE_RATE_LIMIT_HEADER` names the header identifying a client; it was unset, and password guessing was unlimited. Caddy writes `X-Client-IP` from the connecting address on every API host, replacing whatever a client sends, so the header cannot be forged. Measured on staging: 52 wrong passwords answered, the 53rd refused with 429, a second address unaffected. Our edge functions reach GoTrue through Kong without the header and are not limited. For a load test on staging, raise `RATE_LIMIT_TOKEN` in its `.env`.
- **Google sign-in is one switch, `GOOGLE_SIGNIN_ENABLED` in `.env`, and it ships off** (plan step 1.6). Empty or `false` keeps GoTrue as it was; `true` turns on its Google provider with `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` and the redirect URI `PUBLIC_URL/auth/v1/callback`. `deploy.sh` refuses any other value, a client id that is not one Google web client id, and a missing secret. **Staging and production may share one Google OAuth client** — owner decision G3, taken 17.09.2026 — and sharing is then declared with `GOOGLE_CLIENT_SHARED=true` in **both** `.env` files: the same `GOOGLE_CLIENT_ID` on both sides without that opt-in is refused, so a shared client is a written decision rather than an accident of editing, and what that catches is the **partial** mistake — the other environment's id pasted into `GOOGLE_CLIENT_ID` while no opt-in was written. The opt-in on one side only is refused too, naming that side and whether the key is missing there or merely not `true`. Empty or `false` means "not shared" and any other value is refused like the switch, so a typo never reads as "not shared". **Be exact about the limit:** once both files carry the opt-in, this check can no longer tell a deliberate share from a wholesale copy of the other environment's `.env`, because such a copy brings the opt-in with it. A copied `.env` is caught by the `PROJECT_NAME` guard, which runs before it, and again by the `JWT_SECRET`, `SMTP_HOST`, `COMPOSE_PROFILES` and `OTP_PEPPER` guards; this check deliberately does not repeat their work. The opt-in is read on the same terms as the comparison it governs — whenever `GOOGLE_CLIENT_ID` is non-empty, whatever the switch says, from whichever side deploys — the peer's spelling is held to the same rule once the ids match, the ids stay compared by hash, and no value is printed. The risk the owner accepted: staging runs a copy of production's accounts, so one client is one consent screen and one token audience across both environments, and a change to the client's redirect URIs, branding or verification state reaches both stacks at once. GoTrue v2.170.0 will not create a Google account while `GOTRUE_DISABLE_SIGNUP` is true, so the auth service's entrypoint opens signup exactly when `GOTRUE_EXTERNAL_GOOGLE_ENABLED` is the string `true`, keeps it closed for an empty value or `false`, and stops the container with exit code 64 for anything else: GoTrue reads that variable as a Go bool, so `TRUE`, `1` or `t` would turn Google on while signup stayed closed and autoconfirm stayed on. That is derived inside the container and not by `deploy.sh`, because `deploy/set-resend.sh` or any hand-run `docker compose up` recreates GoTrue without `deploy.sh`'s environment. The same step turns `GOTRUE_MAILER_AUTOCONFIRM` off: with it on, GoTrue treats every provider address as verified for automatic linking (`internal/models/linking.go`) and would link a Google account whose address Google never verified to the account that owns that address (the conservative answer to a question still open for the owner). Open signup would also let `/signup`, `/otp` and `/magiclink` create accounts, so Kong's `auth-v1-closed` service answers them 403 through `request-termination`, in front of a dead upstream port so a lost plugin fails with 502. Kong 2.8.1 tries prefix paths longest first and normalises the path before matching, so `//auth/v1/signup`, `/auth/v1/./signup` and `/auth/v1/%73ignup` land on the block too (proven against a throwaway `kong:2.8.1`). `kong:2.8.1` has no curl: `deploy.sh` probes the block over bash's `/dev/tcp` inside the container. Phone, anonymous users, SAML and manual linking are literal `false`. `tests/deploy/` pins all of it and runs `deploy.sh`'s checks against fake `.env` files, and `e2e/tests/kong-closed-routes.spec.ts` checks the closed routes and `/auth/v1/settings` on staging itself. The kill switch is `false` plus a redeploy, never a rollback.
- Each environment's `.env` is provisioned by hand on the host and never leaves it. Build-time values (`VITE_*`) live as GitHub environment variables; the deploy key, host and pinned host key are repository secrets.
- `deploy.sh` reads every `.env` key with `|| true`. Under `set -euo pipefail` a bare `grep` that matches nothing ends the script with no message — that exact bug broke production login for a few minutes the first time it ran.

## Architecture

### Provider stack

`main.tsx` mounts `ThemeProvider → AuthProvider → ToastProvider → AppConfigProvider → App`. `App.tsx` then adds `SuperAdminProvider → CompanySettingsProvider → PlanProvider → BrowserRouter` (3.4b swapped the first two: both of the others ask SuperAdminProvider which company the session is in, and it reads only AuthContext). Anything needing `usePlan()` must live below that — which is why the plan-gated routes are all inside `App`, not `main`.

`AppConfigProvider` sits above `App` rather than beside `PlanProvider` because the landing page and the signup screen price plans before anyone is signed in. It loads `get_public_config()` (anonymous) or `get_app_config()` (signed in) per account and holds the price book, the plan feature map and the trial length; `useAppConfig()` reads them, and the seed in `src/lib/appConfigSeed.ts` stands in until the first answer arrives. **It also reads again when the tab regains focus and the last answer is older than `APP_CONFIG_MAX_AGE_MS`** (five minutes, `src/lib/appConfig.ts`), so a session left open for days stops quoting the prices of the day it was opened. That is not a poll: a tab nobody touches asks nothing, and a focus inside the window asks nothing either. `useAppConfig().refresh()` asks immediately, ignoring the window — for the settings screens (plan 3.6c) to call after a write. A part of an answer that is missing or does not parse keeps the value already on screen, not the seed, and only the newest request may install an answer, so a change of account cannot be overwritten by the load it interrupted. See *Settings, the price book and the feature map* below.

### Auth is a chain of gates, not a single check

`App.tsx` is the authoritative map of who may see what. Read it before touching access control. The order is:

1. `authLoading` → spinner
2. no `user` → public routes only (`/`, `/login`, `/signup`, `/auth/*`)
3. `userBlockReason` → `AccountBlockedPage`
4. a Google account whose profile has no company (`needsCompanyRegistration` in `src/lib/googleAccount.ts`) → `CompleteRegistrationPage`, no router at all. Ahead of the company gates because none of them can answer for an account with no company, and the authenticated router would send it to `/overview`, where every tenant query asks for `company_id = null`.
5. `companyApprovalStatus` `pending` / `rejected` / `suspended` → full-page takeover, no router at all
6. `MustChangePasswordGuard` → forces `/set-new-password`
7. `SubscriptionGuard` → forces `/abo-aktivieren` when an approved company's subscription is inactive
8. `PlanGate` per route → `LockedFeaturePage` when the plan tier is too low
9. `isAdmin` / `isSuperAdmin` conditionally *register* the route at all

`AuthContext` also enforces a 20-minute inactivity logout (`SESSION_TIMEOUT`, tracked in `localStorage.lastActivity`).

**There is one sign-in screen, `/login`, and the account decides what happens after it** (owner's decision, 17.09.2026, which reverses the half of plan slice 3.6a that gave the panel its own front door). Nothing knows who a visitor is before they sign in, so the screen is the company one for everybody — Google button, staging banner and all — and `SignInRoute` in `App.tsx` routes the session once it exists: `/admin` for a platform account, `/overview` or the panel page it was heading for otherwise. It is registered in **both** routers, because signing in swaps the public router for the authenticated one and the new router starts at whatever the address bar still says; deciding in a route rather than with a `navigate()` inside the form is what keeps that redirect out of the router being unmounted. `/admin/login` (the front door of 16.–17.09.2026) is **not deleted** — it redirects onto `/login` and carries the remembered return path along, as does a signed-out `/admin/*` or `/super-admin/*`. `/super-admin/*` is the panel's entry of before 3.6a and is **only** a redirect, in both routers: slice 3.13b took the last in-app link off it, and the two routes stay for the bookmarks that already exist. Nothing in the product writes such a path any more. That path travels in the router's location state, never the query string, and `rememberedPanelPath()` (`src/lib/adminGate.ts`) validates it **every time it changes hands**: only a path inside the panel survives, and an absolute URL, a `//host`, a backslash, a `..` segment and either sign-in page are all dropped. A value that decides where a browser goes after signing in is an open redirect the moment it is taken on trust.

**What the unification costs, as measured fact rather than as reassurance — the first draft of this paragraph was wrong in both directions.**

1. **The network surface is unchanged.** `PlatformLoginPage` called the same `AuthContext.signIn` → `signInWithPassword` → `POST /auth/v1/token?grant_type=password`, so the endpoint a platform password is guessed against was never path-gated. What widens is **UI discoverability** — a visitor finds the panel's sign-in without knowing `/admin/login` existed — and **credential stuffing by default**, because a bot that posts to the one form it can see now reaches platform accounts too.
2. **The distinct refusal messages do not reveal whether an address exists.** #57's uniform-refusal rule (`platformSignInMessageKey`, every refusal one sentence, "so the page cannot say who is on the platform team") is **gone**, and `/login` branches instead — a block reason, `auth.error.emailNotConfirmed` *with an "E-Mail bestätigen" CTA*, `tooManyAttempts`, `network`, `generic`. It was not protecting anything an attacker could otherwise learn: GoTrue v2.170.0 verifies the password **before** it reports an unconfirmed address, measured on staging 17.09.2026 against a throwaway unconfirmed `@example.com` account — wrong password → `400 invalid_credentials`, **correct** password → `400 email_not_confirmed`, unknown address → `400 invalid_credentials`. So `email_not_confirmed` only ever reaches a caller who already holds the credentials, and the block-reason branch needs them too (`AuthContext.signIn` returns early on GoTrue's error and asks `checkProfileAccess` only after it succeeds). Do not restore the uniform message on the belief that it closes an oracle; it does not.
3. **What remains is the rate limit's shape, and it is narrow.** `GOTRUE_RATE_LIMIT_HEADER: X-Client-IP` with Caddy overwriting that header from the connecting address on every API host, so the budget is **per source IP**: `RATE_LIMIT_TOKEN` (60) requests per 5 minutes on `/token`, **shared between password sign-ins and refresh-token calls**, with no per-account counter and no lockout anywhere in the product. It bounds a single-host brute force and scales away with rotating IPs; and because the budget is shared, a guesser behind the same NAT as real users can break *their* token refresh. The "52 wrong passwords answered, the 53rd 429" figure elsewhere in this file is one IP against one budget — it does not measure per-account protection, because there is none.

Three rules about how a session comes to exist:

- **Owners of a pending or rejected company stay signed in.** `signIn` signs the session back out only for user blocks and for suspended, inactive or deleted companies; gate 5 then shows the waiting or rejected page. A new owner lands on the waiting page straight after entering the signup code.
- **One-time codes go through `src/lib/otpClient.ts` and nothing else.** Forgot password, the signup verification step, `/auth/verify-email`, `/einladung` and a **company user's** email change on `/mein-konto` all render `OtpChallenge` from `src/components/auth/`. A session returned by `otp-verify` is installed with `useOtpSessionHandoff`, never with a bare `setSession()` followed by `navigate()`: installing it swaps App's public router for the authenticated one, and a `navigate()` issued around that swap can land in the router being unmounted, leaving the new one on the code screen.
- **A platform account's email change has no code** (owner's decision, 17.09.2026), and that is the one exception to the line above. The `email_change` code was mailed to the **new** address, so it proved control of that mailbox and never anything about the account — an attacker at an open tab picks the new address and reads their own code — and the owner hit the wall it created: he could not read the mailbox he was moving to. What was never optional and is now **the only** control left is the other half: a password sign-in recorded in the session token's `amr` claim and no older than `PASSWORD_PROOF_MAX_AGE_SECONDS` (600 s, `supabase/functions/_shared/otp-core.ts`). `otp-request` enforces it for the code path and `POST /platform-staff/email-change` for the direct one; `AccountPage` produces it the same way for both, with `signInWithPassword` against the *current* address. Do not relax it, and do not "simplify" the direct route into a browser-side password check. The route is on `platform-staff` rather than a new function (every new function costs a line in `PUBLIC_FUNCTIONS`/`FUNCTION_ENV` and in `deploy/docker-compose.yml`), it is matched **before** `resolvePlatformStaffRoute` and is deliberately not a row in `PLATFORM_STAFF_ROUTES`: it needs no capability, only an **active** staff row, and its audit row is written by the database. That row is `app_private.audit_write`'s, through `public.platform_self_email_change_record` (service role only, `20260919140000`), with category `auth` and action `auth.platform_email_change` — a namespace `public.platform_audit_record` refuses, so no staff role can forge it through the edge functions' door — and it follows `auditedPlatformWrite()`'s shape: an `attempt` row **before** the address moves, and the route answers 500 `audit_unavailable` without moving it when that row cannot be written. Two guards in `platform_self_email_change_check` are not decoration and the migration's self-check fails a release that loses either: **a banned or deleted account is refused** (`account_blocked`), because GoTrue keeps an issued access token valid through a ban and banning the account is the obvious containment lever; and **five completed changes per account per hour** (`rate_limited`), because every change mails the notice below from the product's Resend domain and an insider could loop it — a cooldown was rejected so that correcting a mistyped address stays immediate. What the route deliberately drops from `otp_issue`'s eligibility is `user_profiles.status = 'active'`: for a platform account the staff row is the authority, so a `suspended` profile no longer refuses the change, and `platform_staff.disabled_at` is the lever that does. Both functions ask `app_private.platform_staff_role_of_account(user_id)`, the **account fact** of `20260919130000` and not the session-gated `platform_staff_role_of` — they answer whether a row exists, and they are reached only through the service role, whose key carries no `sub`; self-check 4c fails a release that swaps them. What is given up overall: nothing now proves the new address exists, so a typo locks the account out of its own sign-in address, and the "your address changed" notice to the **old** address is what makes that visible.
- **A Google sign-in is one button, one marker and one function** (plan 1.6). `GoogleButton` renders **nothing** until `GET /auth/v1/settings` reports the provider enabled (`src/lib/authProviderSettings.ts`, read once per page load, and "off" for every failure), so the screens are unchanged while `GOOGLE_SIGNIN_ENABLED` is false. `src/lib/googleSignIn.ts` sends the browser with `prompt=select_account` and **no `access_type`** — we call no Google API, so a refresh token would be a secret kept for nothing — and leaves a one-time marker in `sessionStorage` that says which screen started the flow. `AuthContext` then settles the session exactly once through `oauth-account`'s `reconcile`, and `nextAfterReconcile` (`src/lib/oauthAccountClient.ts`) is the whole routing decision. Two things must not drift: **platform staff never sign in with Google** (owner decision, 16.09.2026) — the session is ended and `LoginForm` shows why — and the test for that is `sessionCameFromGoogle`, never "the account has a Google identity", or a platform account whose address also exists at Google would be signed out of a correct password sign-in. Since 17.09.2026 that refusal is one pure function, `googleSignInRefusal()` in `src/lib/adminGate.ts`, which AuthContext calls and `adminGate.test.ts` pins; the button itself shows for everyone, because the unified screen cannot know who is looking at it. **The browser's refusal is the message, not the wall.** Since `20260919130000` the database answers NULL to every platform capability asked from a session GoTrue did not mint with a password, so a Google session reaches nothing either way — which is exactly why the browser check must not be "simplified away" on the grounds that the server covers it: drop it and the account gets an empty panel instead of a sentence.

### Multi-tenancy and the two company IDs

Every business table carries `company_id`, isolated by RLS. `AuthContext.companyId` is the logged-in account's **membership** (`user_profiles.company_id`), null for platform staff. `SuperAdminContext.effectiveCompanyId` is the company whose data a screen must actually query. **Every tenant query uses `effectiveCompanyId`** — since 3.4b that includes `useDatabase`, `useFahrtenbuch`, `CompanySettingsContext`, `PlanContext` and `CompanyBillingPage`, which read the membership and so asked for `company_id = null` inside a support session. (An older version of this paragraph said only `MonatsplanungStundennachweisPreview.tsx` used `effectiveCompanyId`. That was wrong in both directions: that file's `effectiveCompanyId` is a local variable off the planning run and it never reads the context at all, while some two dozen files do.)

**Since 3.4b (PR #80) `effectiveCompanyId` comes from the database, not from a click.** It is `companyScope()` (`src/lib/companyScope.ts`) applied to the open context in `platform_whoami().company_context`, so it survives a reload, follows a context closed in another tab and ends when the context does. The order of its branches mirrors `get_active_company_id()`: a member's own company first, the context only for an account that has none — and `platform_context_open` refuses an account that has one (`account_in_company`). Keep `AuthContext.companyId` meaning the membership: `receiptScope()` tells `own_company` from `other_company` by comparing the two values, `ownCompanyDataReadable()` judges the account's own company by the database's answer for it, and AuthContext's own company/approval/subscription queries are about the membership. `companyScope.readOnly` is the browser's copy of "a `view` context writes nothing", and `useCompanyScope()` (`src/hooks/useCompanyScope.ts`) is how a screen asks for `can`, `canCreate`, `canEdit` and `canDelete` with that applied. **`SuperAdminProvider` is the outermost of App.tsx's three providers** so `CompanySettingsProvider` and `PlanProvider` can ask it.

**In the database there are two company helpers, and which one a policy asks is the whole design** (`20260917130000`, plan 3.3):

- `get_user_company_id()` — the caller's membership, whatever state it is in. The predicate of the **account shell**: `companies`, `company_settings`, `user_profiles`, `roles`, `role_permissions`, `company_subscriptions`, `subscription_invoices`, `subscription_payment_audit`. A suspended company's owner has to keep reading those, or the page that explains the suspension, `/abo-aktivieren` and `/billing` would come up empty.
- `get_active_company_id()` — the company whose **business data** the caller may touch, or NULL. It is the predicate of every business table, and it encodes App.tsx's gates one for one: `user_profiles.status` not `inactive`/`suspended`/`deactivated` (`pending_invite` is deliberately allowed — the invitation flow completes on it), `companies.approval_status = 'approved'`, `companies.status` in `active`/`trial`, `subscription_status = 'active'` and an expiry that is absent or in the future. A company or an account the screens refuse now reads and writes nothing, whatever token it holds, and the five planning RPCs and the three Gehaltsquittung RPCs ask the same helper rather than `user_profiles.company_id`. The one deliberate exception is `redeem_activation_code`, the way *out* of a blocked state, which keeps reading the caller's membership — a blocked company is exactly the caller that needs it.

**One shape, everywhere.** A business table carries exactly four policies (`<table>_select|insert|update|delete`, fewer where a command has none): SELECT is `company_id = (SELECT get_active_company_id()) OR (SELECT platform_reads_company_data())`, and every write is the same predicate as USING **and** as WITH CHECK, plus the table's own gate — `current_role_permits('<page>', true)`, or `is_company_admin()` for the four that ask for an administrator. A child table (document blocks and variables, the reconciliation children) asks the same question of its parent. Writing the same predicate twice is what refuses a move between companies. `fahrtenbuch_trips` still has **no UPDATE policy**, and both migrations' self-checks fail if one appears.

**Every company table with a write policy now carries a page** (`20260923130000`, slice C). 3.3 gated the ten tables `20260910120000` had gated and wrote down that it was leaving the rest: *"no role gate today, and none added: a viewer writes these exactly as it does now. Narrowing them is a decision about roles, not about tenancy."* That decision was taken on 23.09.2026, and twenty-three more tables took the `page_key` of the screen that writes them — **`documents`** for the Fahrtenbuch (imports, trips, assignment audit), the five planning tables, the six `historical_*` tables and their three children, the saved Stundennachweise, the document templates and the document blocks and variables; **`cash-balance`** for `cash_transactions`; **`cars`** for `car_driver_assignments`. No `page_key` was created and no `role_permissions` row was written, deliberately: the Rollen screen saves a role by deleting all its rows and re-inserting one per key in `PAGE_DEFINITIONS`, so a key the screen does not know is dropped the first time anyone edits that role. So the rights that move are the ones the seeded roles already implied — `viewer` holds `can_edit` on no page, `editor` holds none on `documents` — and a company that wants an editor to go on planning months ticks *Bearbeiten* on the Dokumente page of that role.

Four tables on the same list stay ungated, each for a reason that already closes it: `notification_settings` (its writes ask `is_company_admin()`, stricter than any page), `cash_movements` and `salary_cash_receipts` (`authenticated` holds SELECT and nothing else; their writers are the three Gehaltsquittung RPCs, which have always asked `current_role_permits('salaries', true)`), and `document_counters` (`REVOKE ALL FROM anon, authenticated`). **SELECT is never gated by a role** — 3.3's shape has no role term there and slice C did not invent one. **A company table added from here on takes one or the other on its writes**, a page or `is_company_admin()`: `trip_analysis_settings` and `driver_month_budget` (`20260922110000`, merged the same day) already do, with the administrator.

Two tables carry one clause more, and it is not decoration: `fahrtenbuch_imports.imported_by` and `fahrtenbuch_assignment_audit.changed_by` must equal `auth.uid()` on INSERT. It is the only thing stopping one member of a company filing an import — the artefact the whole payroll chain hangs off — or the record of who reassigned a trip in a colleague's name, and the page gate beside it since slice C does not replace it: a page says *whether* you may write, never *as whom*. Rebuilding either policy from the tenancy predicate alone silently loses it, and `matrix.sql` cannot see the loss because its INSERT probes supply the caller's own id either way; self-check 10 in `20260917130000`, self-check 2 in `20260923130000`, section 2b of `tests/rls/tenant-state.sql` and section 2 of `tests/rls/permission-coverage.sql` are what catch it. For the same reason **deleting an import or a trip stays `is_company_admin()` alone**: replacing that term with the page would have widened it, because a supervisor holds `can_edit` everywhere.

**A company may name a role of its own since `20260923120000` (slice B), and `admin` is not one of the names it may choose.** `roles_name_key` was `UNIQUE (name)` across every company — so two companies could not both call a role `Disponent`, which is why no company had ever created one — and it is replaced by two partial unique indexes: one per name over the system rows, one per company, on `lower(btrim(name))`.

**That constraint was also a privilege boundary, and this is the part not to undo.** `sync_user_profile_role` (20260302065621) copies `roles.name` into `user_profiles.role` on every write, and that text is read as an *authority* by `is_company_admin()` (`up.role = 'admin'`), by `AuthContext.isAdmin` — which decides whether App.tsx registers Benutzer, Rollen and Einstellungen at all — and by `activation-code-mail.ts`. A company role named `admin`, with no permission row anywhere, would therefore have made its holders company administrators by name. `app_private.enforce_company_role_shape` refuses a company role that takes a system role's name (compared `lower(btrim(...))` on both sides, the expression the index is built on, because a boundary one `lower()` away from flipping will flip), refuses `is_system` on a company role, refuses a later change of kind, and refuses a *system* role that takes a name a company already holds. `app_private.enforce_user_profile_role_scope` is the other half: the profile privilege guard says **who** may change `role_id` and never **what** it may be set to, so without it a company admin could point one of its own profiles at another company's role and `current_role_permits()` would read that role's rows. Section 2f of `tests/rls/company-roles.sql` builds the escalation with the trigger switched off and shows `is_company_admin()` answering true, so the guard cannot be mistaken for a naming convention.

**`public.company_role_save` and `public.company_role_delete` are the screen's one transaction per role, and they are SECURITY INVOKER on purpose** — the policies of `20260917130000` and `20260923110010` stay the boundary, and the functions add only atomicity, argument validation and a stable reason. Three consequences:

- **`matrix.sql` is silent about them by construction.** Its uncovered-function sweep filters on `p.prosecdef`. A new SECURITY INVOKER function in `public` is never reported, so it needs its rpc line written by hand and a file of its own; `tests/rls/company-roles.sql` section 7a asserts they are still INVOKER, so a change to DEFINER is caught somewhere.
- **Nothing on a caller's own path may name `app_private`.** Both RPCs, both trigger functions and the two helpers `public.role_page_keys()` and `public.role_name_is_system_reserved()` run as the caller, and `authenticated` holds no USAGE on that schema and no EXECUTE on anything in it. A call from any of them is `42501 permission denied` — and in `company_role_save` that is `insufficient_privilege`, which its own handler catches and reports as `not_authorized`, so the feature fails silently and blames the administrator's role. The file shipped that way once and the kit caught it; self-check 9 and section 7d are the rule rather than the instance. That is also why the two helpers are in `public` rather than beside `plan_feature_keys()` in `app_private`, and why `service_role` holds EXECUTE on them too — it writes `roles`, so it fires the trigger.
- **`company_role_save` replaces a role's permission rows wholesale**, and the payload is built from `PAGE_DEFINITIONS` alone, so a stored `page_key` this build does not know is dropped the first time anyone edits that role, with a success toast. `public.role_page_keys()` is the database's copy of that list and `src/utils/rolePageKeys.test.ts` reads the newest migration defining it and fails when the two differ — `planFeatures.test.ts`'s rule for the other list held in both places. A new screen adds its key to `PAGE_DEFINITIONS` and to that function in the same release. Every boolean in the payload is compared with `IS NOT DISTINCT FROM`, never `=`: an absent `can_view` is SQL NULL, and `=` made the "edit implies view" guard fail **open**.

**Storage has two terms, because a bucket policy cannot tell a read from a write the way the refusal trigger does** (`20260920100000`, the file half of plan 3.C). Every company bucket keys on the first folder of the object's name. **Read** is `folder = get_user_company_id()` — a member's own company in whatever state, and a platform account's opened company in either mode. **Write** (INSERT, UPDATE, DELETE) is `folder = COALESCE(<the caller's user_profiles.company_id>, platform_support_company_id())` — the membership, or for a company-less account only the company of an open **support** session. Never write a storage write policy on `get_user_company_id()`: that is exactly the defect this closed, a `view` context writing the `documents` bucket. Each bucket keeps its own member gate beside that: none on `documents`, `fahrtenbuch-files` and `stundennachweise-pdfs`; `role IN ('admin','super_admin') OR is_company_admin()` on `company-logos`; `fahrtenbuch-files` has no UPDATE policy; `salary-receipts` (3.3's shape, `get_active_company_id()` and `current_role_permits('salaries', true)`, no DELETE) already followed the rule and was left alone. The policies keep production's names, captured read-only on 19.09.2026, and the migration refuses a database where any other policy names one of the four buckets. `document-templates` is owner-keyed and unused; the private bucket named `Y & A Mobility` is named by no policy at all and waits on the owner.

**Two named seams belonged to 3.4**, so the support-session slice changed two function bodies instead of 150 policies: `platform_reads_company_data()` and `platform_writes_company_data()`. **Both are `SELECT false` since `20260917140000`** (plan 3.4a), and three self-checks say so — that migration's, and `20260923100000`'s, which re-asserts it because every business table's SELECT sits in an OR beside the read seam, so one `true` would reopen all of them at once. A platform account therefore reaches a company's business rows only through the company its open context names — `get_active_company_id()` and `get_user_company_id()` answer it for a company-less staff account — or through the audited read models of 3.6b, and writes them through a support session or the audited RPCs of 3.5. No `HOLE[3.4]` cell is left in `matrix.sql`.

### Platform staff, capabilities and the audit log

Platform rights live in `app_private.platform_staff` (since `20260916110000`): one row per platform account, with a fixed role — `owner`, `support`, `billing` or `read_only` — and `disabled_at`. **`user_profiles.is_super_admin` grants nothing.** It only tells the browser where to route; `app_private.platform_staff_sync_profile()` keeps it in step with the table. The self-check of `20260916110010` fails a release if a policy, a view, or any function other than that trigger, `enforce_user_profile_privilege_guard` and `app_private.signup_insert_company` (which writes `false` for the owner it creates) mentions the column.

- **The capability matrix is written down once**, in `app_private.platform_capability_matrix()` (plan 3.A). Changing who may do what is a migration that replaces that function; `tests/rls/platform-authority.sql` restates it and fails on any difference. `support` has no `companies.lifecycle` (open decision D2) and `read_only` no `audit.read` (D3).
- **Helpers.** `public.platform_staff_role()` returns the active role or NULL, `public.platform_can(capability)` a boolean; both are for signed-in callers only (every policy that calls `platform_can` applies `TO authenticated`, so `anon` holds EXECUTE on neither), and wrap them in a policy as `(SELECT public.platform_can('…'))`. `public.platform_whoami()` (authenticated only) returns `{role, capabilities, company_context}`; `company_context` was null until `20260917140000` and carries the open context since. `public.platform_can_manage_account(user_id)` (authenticated only) answers whether the caller may act on one account as platform staff: an account with a staff row, a disabled one included, needs `staff.manage`, any other one `company_users.manage`. `public.account_is_platform_staff(user_id)` (service role only) answers whether an account has a staff row, a disabled one included, for callers acting with the service role. SECURITY DEFINER code that has a user id rather than a session uses `app_private.platform_staff_role_of(user_id)` and `app_private.platform_role_can(role, capability)`. Each answers false or NULL, never an error, to a caller it grants EXECUTE who holds no role.
- **`is_user_super_admin()` is "has an active staff row", whatever its role, and false, never NULL, for anyone else.** Platform sign-in is an address and a password with no second step (the owner's decision of 16.09.2026), so no *verification* condition belongs in it — but since `20260919130000` it answers false for a session that was not established with a password, because it reads `platform_staff_role_of()` like everything else (below). Since `20260917130000` (plan 3.3) **neither a policy nor any function a policy calls reads it any more** — the same migration took the `is_user_super_admin() OR …` term out of `current_role_permits()`, where it had survived one indirection below the policy text and gated ten business tables, and its self-check fails a release where either comes back. Every platform branch now names a capability (`companies.read`, `companies.lifecycle`, `companies.hard_delete`, `billing.manage`, `pricing.manage`, `settings.manage`, `company_users.manage`) or the read seam `platform_reads_company_data()`, so a `support`, `billing` or `read_only` account no longer holds an owner's writes. The function itself stays: `platform_whoami`, `otp_issue` and the browser's routing still ask whether an account is staff at all.
- **A platform capability requires a password-backed session** (`20260919130000`). The owner's decision of 16.09.2026 — platform staff never sign in with Google — was a screen until then: `sessionCameFromGoogle()` ended the session in the browser, but the token itself passed every `platform_can()` check against PostgREST or an edge function, and for an account that merely *linked* Google to a password account the browser has nothing to go on but the marker the tab left in `sessionStorage`. The rule now lives in the database, in the one function every session-facing platform path reaches: `app_private.platform_staff_role_of(user_id)` returns NULL when the request carries an end user's token (`app_private.jwt_has_subject()`) and `app_private.session_amr_permits_platform()` is false — a condition about the *session*, so it holds for every account the caller asks about. So `platform_can`, `platform_staff_role`, `platform_whoami`, `platform_can_manage_account`, `platform_audit_record`, `is_user_super_admin`, the five read models, both settings RPCs, every write RPC's capability check and the profile privilege guard all refuse together, and there is no second place to forget.
  - **The rule is an allow-list**: the `amr` claim must name `password`, and must not name `oauth`, `sso/saml` or `anonymous` (MFA *appends* to a session's `amr`, so "contains password" alone is not enough). A missing, empty or malformed `amr`, and a caller with no JWT, are all false — never NULL and never an error. GoTrue v2.170.0's method strings are in `internal/models/factor.go`; a refresh rebuilds `amr` from the session and adds nothing (`token_refresh.go`, and measured on staging: the same array and the same timestamp after a refresh), so the rule does not expire with the access token.
  - **`POST /verify` records `otp` whatever the `type` is** (`verify.go:279`), so the session `issueSession()` mints after a one-time code holds no capability. That is the rule's one cost and it is deliberate: a newly invited platform member and one who used "Passwort vergessen" have both just chosen a password, and `SetPasswordPage` now ends such a session for a platform account and sends it to `/login` — the one sign-in screen since 17.09.2026 — to use it.
  - **The audit log still records the role the *account* holds.** `app_private.audit_write` reads `platform_staff_role_of_account()` for `actor_role` (`20260919130000` restates `20260916110000`'s body with that one call renamed and every other rule carried over). On the gated helper it would have written NULL on exactly the event the rule exists to catch: the only row a refused session still produces is `platform_rpc_authorize`'s `denied` one, which is written for any actor, and a NULL role there is indistinguishable from an ordinary company user's refusal.
  - **`amr` is read out of the document the `sub` came from**, singular claim first, which is the order `auth.uid()` checks — so the session every capability lookup resolves the caller as and the sign-in method judged here can never be two different sessions. An `amr` with no subject beside it is not a session's `amr` and reads as none. **One exception, and it is storage-api's shape** (`20260920100000`): storage-api v1.19.3 sets the singular `request.jwt.claim.sub` and the whole payload as `request.jwt.claims`, and **no** singular `amr`. Read strictly, that request had no sign-in method, so every platform account held no role on every storage-api request and a support session reached no file. `jwt_amr()` therefore reads the document's `amr` when the singular subject carries no singular `amr` at all **and the document names the same subject** — the same token either way. A singular `amr` still wins, a malformed one does not fall back, and a document naming anyone else is never read. A migration that restates `jwt_amr()` must keep this, or storage breaks for platform accounts with no error anywhere.
  - **The condition is the session, and it never asks `auth.uid()`.** A trigger, a migration, GoTrue and the service role carry no `sub` claim — the service key holds a `role` and nothing else — so nothing that holds a user id without a session changes. Asking `auth.uid()` would be two defects: its body is not ours and differs between the supabase/postgres image (singular claim only) and the live databases, and `p_user_id = auth.uid()` is a three-valued comparison that fails **open** on one NULL. The first version of the migration did exactly that and the RLS kit caught it. The account fact keeps its own name, `app_private.platform_staff_role_of_account(user_id)`, and the other two callers that ask about a *row* rather than a session read it: `platform_staff_sync_profile()` and `enforce_user_profile_privilege_guard()`'s `staff_flag`. - **The browser** asks `platform_whoami()` in `SuperAdminContext` (`platformAccess`, `platformCan`, `isPlatformStaff`), and only when the profile flag says the account is worth asking. `AdminLayout` opens the panel only for an active role; `AdminSidebar` and the platform pages hide what the role lacks, and entering a company needs `business.read`. None of that is the boundary: the database checks every action again.
- **The profile guard (`enforce_user_profile_privilege_guard`)**: a JWT without a subject (the anon key) writes no profile at all, even inside a SECURITY DEFINER function where RLS does not apply; no JWT changes a profile's `user_id` or `company_id`, a platform account's included; a JWT sets `is_super_admin` only to what `platform_staff` already says; and a company admin's exceptions for role and status do not reach a profile with a staff row. The service role, GoTrue and migrations are not guarded.

### One subscription model: coverage in, three columns out

Since `20260919150000` (plan 3.F, step U1) `companies.subscription_status`, `companies.subscription_expires_at` and `companies.plan` are **derived**, not assigned. `public.subscription_coverage` holds the periods a company is paid or granted — one row per period, with its `source` (`invoice`, `activation_code`, `manual`, `trial`, `migration`), its `plan`, its `price_cents` (**integer cents**, and **NULL on every path but an invoice's** — see below), a `status` of `active` or `void`, and a `grants_access` flag. `app_private.recompute_company_subscription(company_id)` reads them and is **the only writer of `subscription_status` and `subscription_expires_at`**, and the only thing that *derives* `plan` (which has a second writer — see below); it never touches `companies.status`, `.approval_status`, `.subscription_started_at` or `.subscription_duration_type`. Its rule, in order: an open-ended granting row → `('active', NULL)`; the newest granting end ahead of now → `('active', that end)`; a granting row that has passed → `('expired', that end)`; otherwise the newest live end at all, `expired` if it has passed and `inactive` if it has not; nothing live → `('inactive', NULL)`. The tier comes from the period that decides access now — live, granting and **not ended** (`period_end IS NULL OR period_end > now()`), open-ended first, then the furthest end — so it is derived only in the two branches that answer `active`; in the other three `plan` stands (`20260920150000`). U2 (`20260919170000`) made invoices a source of coverage, and U3 (`20260920120000`) refuses every direct write of the columns from the API roles.

What follows is easy to break:

- **A write records a period and calls the recompute, in the same transaction.** `redeem_activation_code`, `update_company_subscription_manual` and `platform_company_set_plan` do this; a new writer does the same through `app_private.subscription_coverage_record(...)`, which records, optionally voids the company's earlier live rows (`p_replace`), and recomputes. Assigning either derived column directly is what the migration's self-check 7 fails on, and since U3 the database refuses it too (below). **`plan` has two writers on purpose:** `platform_company_set_plan` assigns `companies.plan` — a company with no coverage has no period for a tier to be derived from, and the screen must still be able to set one — and carries the tier onto every live granting period **that has not ended**, current *and* future. Dropping the future half is a silent downgrade: an early renewal's row starts ahead of today, the recompute reads the plan from the granting row with the furthest end, so the next sweep would write the old tier back. Self-check 7b pins both halves. **The recompute reads a tier from exactly the set set_plan carries onto** — live, granting, not ended, and no term on `period_start` — and that symmetry is the rule: keep the two predicates identical. Until `20260920150000` the recompute's tier query had no end filter, so for a company whose every granting period had ended set_plan carried the tier onto nothing, the recompute read the old tier off the ended period, and the next recompute (any coverage write, any invoice RPC, the nightly sweep) wrote it back over the owner's change. Now `plan` stands when no such period exists, as it does for a company with no coverage. **One path still loses the tier, and it is U2's, not the recompute's:** `app_private.subscription_invoice_apply` moves an invoice's row in place and never rewrites its tier, so an ended invoice period that set_plan left at the old tier comes back when the invoice is marked paid, and then it decides. `tests/rls/subscriptions.sql` section 9 records it as `HOLE[revival]`; closing it flips that line. **A void is revived by its reason, never by a re-apply** (`20260921130000`). The function brings a void invoice period back only when `void_reason = 'invoice_canceled'` and the invoice is no longer cancelled, or when it is `replaced` and the caller is `platform_invoice_mark_paid`, the one caller that passes `p_reinstate => true`. Everything else answers `superseded` and writes nothing, so a manual `expired` survives the sweep. The cancel branch and `p_replace` both void live rows only, so neither relabels the other's void; keep it that way, or a cancel-then-un-cancel revives what an administrator withdrew. The self-check fails a release where another function passes a second argument.
- **There is one suspension state, `companies.status = 'suspended'`, and the client reads it.** `approval_status` and `subscription_status` no longer admit the value and their CHECK constraints refuse it, so `platform_company_set_approval('suspend')` writes `companies.status` (and `update_company_subscription_manual('suspended')` records a period that grants nothing — see the last bullet). A recompute never lifts a suspension, and resetting that one column is now enough to bring a company back. **That last part is why this slice touches the browser.** `AuthContext.checkProfileAccess()` reads `companies.status` but runs only on `signIn`; `loadUserProfile`, the path every reload and token refresh takes, read `approval_status` and `subscription_status` and not `status`, so App.tsx's gate 5 fired on whichever of those two the suspension happened to sit in. Emptying them without teaching the client would have sent a suspended company to `/overview` and told it through `LockedFeaturePage` that its *plan* was too low. `AuthContext.companyStatus` is now read in both company queries and the gate asks it; `SuperAdminDashboard`'s Freigaben table, which renders one badge from `approval_status` and has no status column, reads it too.
- **Redeeming a code on an open-ended company no longer caps it.** Before U1 `redeem_activation_code` overwrote a NULL `subscription_expires_at` with `now() + 1 month`, taking open-ended access away from exactly the companies the 2026-06-21 backfill had left open. Rule 1 keeps them open: the open-ended coverage row outranks the code's bounded one and the expiry stays NULL.
- **Invoices grant access since U2** (the owner's three rules of 18.09.2026). A paid invoice covers the calendar month it names, in Europe/Berlin. An open or overdue one grants until two business days after its due date (`app_private.subscription_grace_business_days()`, Monday to Friday, no public holidays). A cancelled one has its row voided and keeps its record. It is one coverage row per invoice, moved in place, never a second one. The two daily sweeps are `app_private.subscription_invoices_apply_all()` and then `app_private.recompute_all_company_subscriptions()`, and **nothing calls them**. Wiring them is a host step, staging first, and HANDOFF.md carries the exact lines and the dry run to take first.
- **`price_cents` is filled for invoices only.** U2 converts once, `round(amount * 100)` in `app_private.subscription_invoice_apply`, and prices a period at the invoice's `amount`, not at what was handed over. The backfill, a redemption and a manual grant still write NULL: none of them knows what a period cost. `company_subscriptions.monthly_price` is a rate, not a price.
- **The subscription modal is the Abo-Status, not a lifecycle control.** `update_company_subscription_manual` accepts `suspended`, records the period and grants nothing — which blocks the company the way the stored word used to — and does **not** write `companies.status`. Suspending a company is `companies.lifecycle`'s act, owners-only under D2, while this RPC asks `billing.manage`; writing the status here would hand billing an owner's act, and a one-way one, since nothing in the modal clears it.
- **Nothing writes the five columns directly (U3).** `subscription_status`, `subscription_expires_at`, `subscription_started_at`, `subscription_duration_type` and `plan` on `companies` are guarded by the `refuse_direct_subscription_write` trigger. It refuses (42501) a change made as `anon`, `authenticated` or `service_role`: a PostgREST PATCH or INSERT through the `companies` policies, or an edge function holding the service key.
  - **It refuses a change, not a mention.** It compares NEW with OLD, so a statement that carries a column's current value passes. An INSERT must leave the five at `'inactive'`, NULL, NULL, NULL and `'basic'`.
  - **Writers are told apart by `current_user`, not by a setting.** Every sanctioned writer is SECURITY DEFINER and runs as its owner, and the authenticator can become only the three API roles, so no GUC or claim is read.
  - **The trigger function must stay SECURITY INVOKER.** As a definer, `current_user` would always be its owner and it would refuse nobody. Self-check 2 fails a release where that changes, and self-check 5 fails one where a sanctioned writer loses SECURITY DEFINER, because the wall would then refuse the product's own path.
  - **What it cannot do is tell one SECURITY DEFINER function from another, or stop a superuser at psql.** That is the job of `app_private.subscription_column_writes()`, a catalogue reader over every function in `public` and `app_private`. Its answer must be exactly: the recompute (status, expiry, plan), `platform_company_set_plan` (plan), `redeem_activation_code` and `update_company_subscription_manual` (start, duration word), and `app_private.signup_insert_company` (plan and `'inactive'`, on INSERT). A new writer fails the migration's self-check and `tests/rls/subscriptions.sql` section 8. If it is sanctioned, add it to both lists in the same commit.
  - **An operator records a period, never an UPDATE.** Use `app_private.subscription_coverage_record(...)` as `supabase_admin`; `postgres` has no USAGE on `app_private`. The next recompute undoes a hand-written value, which is why `e2e/setup-staging.sh` records coverage now.
  - `src/utils/subscriptionDirectWrites.test.ts` is the same rule in code. A `.from('companies')` update, upsert or insert that names one of the five, or whose payload it cannot read, fails the build.

`tests/rls/subscriptions.sql` covers the recompute's five branches, the backfill against seven of the U0 conflict classes, suspension outranking coverage, redemption, the invoice rule, the wall and its catalogue, the table's shape, and a tier set on a company whose periods have all ended (section 9, with the revival path recorded as `HOLE[revival]`). The backfill rule itself is `app_private.subscription_backfill_company(uuid)` — a function rather than a `DO` block precisely so the kit can call it, since the fixture carries no companies for a migration-time loop to touch.

### Plan gating

`PlanContext` maps `FeatureKey → minimum Plan` (`basic` < `advanced` < `premium`), and since `20260916150000` that map is **the `plan_features` setting in the database**, not a constant: `useAppConfig().planFeatures`, with `SEED_PLAN_FEATURES` standing in until the answer arrives. **A feature the map does not name needs premium** — a build that knows a screen the database has not heard of locks it rather than opening it. That rule is fail-closed on purpose and stays; since `20260917120000` it is the second wall rather than the only one, because the database now refuses to *store* a map that does not name every feature this build knows (below). Three behaviors are easy to miss: a company **in a running trial** gets `effectivePlan = 'premium'` regardless of its stored plan, a super admin's `can()` always returns `true`, and `minPlanFor(feature)` (what `LockedFeaturePage` prints) reads the same live map, so the gate and the message can never disagree.

**The state machine behind `can()` is `src/utils/planState.ts`, not the provider**, so it can be tested without a renderer, and **it asks the server's question**: `buildPlanState` reads `subscription_status` and `subscription_expires_at` beside `status` and `trial_end`, and `subscriptionIsActive()` is the one place the browser spells `subscription_status = 'active' AND (expiry IS NULL OR expiry > now())` — `AuthContext.isSubscriptionActive` calls it too. That is not decoration. The normal path leaves a paying customer on `companies.status = 'trial'` for ever: signup writes `trial` with `subscription_status = 'inactive'`, approval changes only `approval_status`, and `redeem_activation_code` writes the five `subscription_*` columns and **never** `status`. Reading `status` and `trial_end` alone therefore turned every customer into `trial_expired` on the day the trial window closed and locked all ten gated routes, while `get_active_company_id()` — which accepts `status IN ('active','trial')` and never reads `trial_end` — went on answering. Since 17.09.2026 (owner's approval, class 3 of the subscription decision sheet) **a live subscription makes a company active on its stored plan whatever `status` says**, the same term gates the `active` branch so the browser is never more permissive than `get_active_company_id()`, and `isTrialExpired` means "the trial ended and nothing replaced it" — `TrialBanner` and the overview's plan card print *Nur Basic-Features verfügbar*, which must not reach a paying customer. The **one** deliberate gap: a *running* trial stays unlocked although a fresh company's subscription is `inactive` and the server refuses it; `SubscriptionGuard` holds such a company on `/abo-aktivieren`, `/aktivierung` and `/billing`, so nothing is reachable through it. `PlanContext` fetches its own company row rather than reading AuthContext's copy, because AuthContext sets the profile one round trip before it has the company — and anything that changes the subscription in-session (`ActivationPage`) refreshes the plan as well as `AuthContext`. **The platform's own screen asks the same helper**, through `readsAsTrial()` in `SuperAdminDashboard.tsx`: judging a trial by the date alone made every paying customer an expired trial there too, on the screen the owner opens daily, while its own overview said *Aktiv*. A status the build does not know locks rather than opens, like a plan it does not know.

Add a new gated feature by extending `FeatureKey` in `PlanContext.tsx` and `SEED_PLAN_FEATURES` in `src/lib/appConfigSeed.ts` (typed `Record<FeatureKey, Plan>`, so a missing seed fails to compile), adding `FEATURE_LABEL_KEYS` in `App.tsx`, wrapping the route in `<PlanGate>` — and **seeding the key into `plan_features` in a migration**, or every plan sees it as premium. That migration also adds the key to `app_private.plan_feature_keys()`, and the two move together: `src/utils/planFeatures.test.ts` reads the newest migration that defines that list and fails when it and `SEED_PLAN_FEATURES` differ, and `20260917120000`'s self-check fails a release whose stored map does not name every key on the list.

### Settings, the price book and the feature map

Since `20260916150000` the prices and the plan feature map live in `app_private.platform_settings` (one JSON value per key, with a `version` every write bumps), not in code. That migration seeded two keys, with the values the constants held: `price_book` and `plan_features`; plans 3.10 and 3.11 added nine more (below).

**The pricing rule, in both engines:** the price per car is **integer cents** per plan, the fleet discount tiers and the yearly discount are **whole percents**, and

```
monthly = cars × price per car × (1 − fleet %)
yearly  = monthly × 12 × (1 − yearly %)
billed  = yearly for the cycle 'yearly', monthly otherwise
```

`compute_plan_price(plan, cars, cycle)` keeps its signature and its edge cases (a NULL car count counts as 1; a count below 1 is billed as one car but looks its tier up with the count as given; an unknown or NULL plan pays the basic price; any cycle but `'yearly'` is monthly) and now reads the book, through `app_private.price_book_price(book, …)`. `calcPricing(book, …)` in `src/utils/pricing.ts` takes the book as its first argument and computes the same. **No price is written anywhere else** — the only copy outside the database is `SEED_PRICE_BOOK` in `src/lib/appConfigSeed.ts`, and `appConfigSeed.test.ts` fails when it and the migration's seed differ.

Four tests keep the two engines together, and the fourth is the one that matters: `pricing.parity.test.ts` pins today's 42 numbers, `appConfigSeed.test.ts` compares the TypeScript seed with the migration's, a `DO` block in the migration compares 42 combinations against `20260911120000`'s body in SQL, and **an alien price book in `tests/rls/pricing.sql` is priced by both engines from the same 42 listed numbers** — a formula that ignored the book and kept a constant would pass the first three and fail only that one.

Reading and writing: `platform_settings_get(key)` needs `settings.read`, and **billing holds that capability for `price_book` alone** (plan 3.A says "settings.read … billing ✓ (prices)", which no single capability can express), so for billing any other key is `forbidden` where a role with plain `settings.read` is merely told it is `not_found`. `platform_settings_put(key, value, expected_version)` needs `pricing.manage` for `price_book` and `settings.manage` — owner only — for every other key, **`plan_features` included**: `pricing.manage` is held by billing as well as owner, the feature map decides what every customer may open, and a feature the map does not name reads as premium, so one billing write of `{}` would lock every gated screen for every non-trial company on basic or advanced. Plan 3.A lists "features" under `settings.manage`. It validates the value's shape per key, refuses a stale version, and records the value before and after. A key with no validator is refused as `unknown_key`: **plan 3.10 and 3.11 add their validators and seed their keys in the migration that introduces them.** Since `20260917120000` a `plan_features` value must also **name every feature key the application knows** — `app_private.plan_feature_keys()`, the sixteen `FeatureKey`s — because the browser reads a feature the map does not name as premium, so one write of `{}`, or of a map with a key dropped by a typo, would put every gated screen of every non-trial company below premium behind `LockedFeaturePage` with no error and no warning. A short map is refused as `invalid_value` with `problem` `plan_features.missing.<the first missing key>`, and the answer also carries `missing_features`, all of them, for the settings screen to name. Keys this build does not know stay valid: that is how a feature is seeded before the release that gates it. Every call by an active staff role writes an audit row — a read as category `read` naming only the version it returned, a write as `settings` — and a refusal is audited too; a caller who is not platform staff is refused with no row at all, as in `platform_audit_record`. **One actor gets at most 120 settings rows a minute** (`app_private.platform_settings_rate_limited`, `20260917120000`): `platform_audit_record`'s number, counted the same way, over one budget shared by reads and writes, because `read_only` holds `settings.read` and the log is append-only. Past it both RPCs answer `{"ok": false, "reason": "rate_limited"}` and write **nothing** — a row saying "you have written too many rows" is the row the cap exists to stop — and unlike `platform_audit_record` they refuse by return value rather than raising, because these two raise only on a broken argument contract. The check sits after the staff lookup and before the capability check, so it covers the `denied` row of a refused capability too. **This slice does not redefine `platform_audit_record`**: 3.5's action allow-list already refuses every `platform_settings.` action, which is stricter than a reserved namespace, and a redefinition here would sort after `20260916150000_platform_audit_record_allowlist.sql` and silently drop both of that function's rules. `tests/rls/pricing.sql` section 8 and self-check 8 in the migration assert the refusal instead, so the property this slice depends on still fails loudly if it ever goes away.

`get_public_config()` (anyone: the price book and the trial length) and `get_app_config()` (signed in: plus the feature map, the feature flags and the announcements that apply to the caller) are what the browser reads, through `AppConfigProvider`.

**Thirteen keys exist**, and every one but `price_book` is `settings.manage` — owner only — to write and `settings.read` (owner, read_only; not billing) to read: `price_book`, `plan_features`, `seller`, `trial`, `invoice` (3.10's first half, `20260919120000`), `mail.sender`, `mail.template.signup_verify|password_reset|invite_activate|email_change` and `feature_flags` (`20260920130000`), and `legal.impressum` and `legal.privacy` (`20260921120000`). **A validator is added by restating `app_private.platform_settings_problem` — the one function that must be copied to learn a key — so restate it once per release, carry every existing branch character for character, and give the copy a self-check that re-states what the old branches refuse** (`20260919120000` and `20260920130000` both do). Never restate `platform_settings_get`, `platform_settings_put` or `platform_audit_record` to add a key. The per-actor budget counts the actions in `app_private.platform_settings_audit_actions()`; a new database-written settings action goes on that list, and `platform_audit_record`'s allow-list must never name one.

- **The trial** is the `trial` key since `20260919120000`: `signup_insert_company` applies `make_interval(days => app_private.signup_trial_days())`, which answers 14 for a missing or malformed document and is what `get_public_config()` quotes, so the quoted and the given number cannot come apart. Changing it moves no existing `trial_end`.
- **The seller** is printed on every invoice PDF: `SubscriptionBillingPage` reads it when it builds the PDF, through `public.platform_invoice_seller()` — `companies.read`, the capability that reads an invoice, so billing and support get it although neither may read the settings; one audited `read` row per call; `not_found` for a document its validator would refuse, and then no PDF is built. `invoiceSellerFields()` (`src/lib/platformSettings.ts`) keeps the old `company_settings` composition. The `invoice` key (number prefix, digits, default payment method) is stored and **still read by nothing**.
- **The mails.** `mail.sender` is the From display name of every mail the edge functions send (never the address, which stays `SMTP_SENDER` on Resend's verified domain; GoTrue's own mails keep `SMTP_SENDER_NAME`). `mail.template.<purpose>` is an **override** of the subject, heading, paragraphs and button label, seeded `{}` so every mail is byte-identical until the owner changes a field; a field left out follows the default in `supabase/functions/_shared/mail-template.ts`, which the functions, the settings screen's preview and vitest all import. **The code never reaches a subject**: no variable is allowed there, `{code}` is not a variable anywhere, six digits in a row are refused, and `safeSubject()` replaces a subject containing the code at send time. **A template this build cannot read sends the default wording, never no mail** — `loadMailDeliverySettings()` never rejects. The functions read both through `public.mail_delivery_settings(purpose)`, service role only and unaudited. `platform_login` has no template.
- **Announcements** are rows in `app_private.platform_announcements`, each with its own version, behind `platform_announcements_list` (`settings.read` without billing), `platform_announcement_save` and `platform_announcement_delete` (`settings.manage`), all audited and inside the settings budget. The window is **two `timestamptz`, never dates**, and the validator refuses a time without an explicit offset, so no cast depends on the session's zone. `get_app_config()` returns those whose window contains `now()` and whose audience (all, `companies.plan`, or named company ids) includes `get_active_company_id()` — so a blocked company and a platform account outside a support session get none — at most five, and **never the audience**. `AnnouncementBanner` (in `AppLayout`) remembers a dismissal per browser by id and version.
- **Feature flags**: `useFlag(key)` (in `AppConfigContext.tsx`) is off for any flag the map does not name. Nothing reads a flag yet. `parseAppConfig` treats an answer without flags or announcements (`get_public_config()`) as none, so an account's announcements never outlive its session.
- **The legal pages** (`20260921120000`). `/impressum` and `/datenschutz` render `legal.impressum` (any of fourteen fields, each justified in the migration header) and `legal.privacy` (`{}` or `{as_of, paragraphs}`, plain text, **32000 bytes** — the one key dispatched ahead of the shared 16384 bound, because `audit_write` refuses a before/after value above 32768). Both read through `public.get_legal_pages()`: anon and authenticated, STABLE, unaudited like `get_public_config()`, and it **reads the two legal keys and never `seller`** — the self-check fails a body that names it. **Never store an Impressum field in `seller`:** the previous release reads a seller only when it names exactly its eleven fields, so a rollback would break the invoice PDF; the panel's copy button fills the Impressum from the seller only when the owner presses it. `App.tsx` matches both paths ahead of every gate, like `/design-preview`; the Impressum renders only once its own `legal_name` is filled. The fourteen public fields are pinned in `tests/rls/legal-pages.sql` and against `IMPRESSUM_FIELDS` in vitest — adding one is a data-protection decision.

### Data access

There is no repository layer. Components call `supabase.from(...)` directly (~63 files), with `src/hooks/useDatabase.ts` covering only the older receipt/driver/income/salary CRUD — and that hook falls back to `localStorage` when Supabase is unreachable, which is a legacy quirk, not a pattern to extend.

Supabase caps a query at 1000 rows, so trip loading is paginated with `while (true)` + `.range()` batch loops. That pattern is deliberate — don't "simplify" it into a single select.

Writes that RLS forbids go through `SECURITY DEFINER` RPCs: `apply_monthly_planning_run`, `replace_monthly_planning_run`, `reassign_fahrtenbuch_trip`, `redeem_activation_code`, `update_company_subscription_manual`, and others in `supabase/migrations/`. Since `20260917130000` the five planning RPCs and the three Gehaltsquittung RPCs (`confirm_salary_cash_payment`, `void_salary_cash_receipt`, `attach_salary_cash_receipt_signed_copy`) resolve the caller's company with `get_active_company_id()`, so running past RLS no longer means running past the company and account state — a suspended company's admin gets each function's own `caller has no company`, and the Gehaltsquittung ones its `Keine Berechtigung` (`not_authorized`). `redeem_activation_code` is the deliberate exception and keeps reading the caller's membership from `user_profiles` itself: it is how a lapsed company comes back, so the active helper would refuse precisely the caller who needs it.

**Running past RLS means running past the role gate too, so each of these asks it itself.** Since `20260923130000` the five planning RPCs ask `current_role_permits('documents', true)` — the page their tables carry — immediately after their own `caller has no company` branch, and refuse with 42501 and HINT `not_authorized`; the state refusal still comes first, which is what `tests/rls/tenant-state.sql` section 4 asserts. The three Gehaltsquittung RPCs already asked `current_role_permits('salaries', true)` and are unchanged. **`get_weekly_abrechnung`, `get_monthly_abrechnung` and their two per-driver siblings need no gate and are not on this list at all**: they are `SECURITY INVOKER`, so the caller's own policies on `income`, `receipts` and `cash_transactions` answer them. If one ever becomes a definer it needs a gate, and section 4 of `tests/rls/permission-coverage.sql` is where that shows up.

**How a screen moves (the batch-1 pattern; the next batches copy it).**

- **Look only, verified as text.** The component's logic — state, effects, queries, handlers, calculations, exports — stays byte-identical, and the new markup goes below a `// ── Presentation (phase 5)` line and only draws. Verify it by comparing the old block with the new file as a substring, not by eye. Where presentation sits inside logic (a config map holding both the words an export reads and the colours the screen paints), split it: the logic half stays, the look moves out. Do not move logic into a hook in the same change: a moved block cannot be checked as unchanged.
- **Where the screens produce statutory documents, batch 3's proof checks more.** Batch 3 moved such screens, and its `design-harness/identity-batch3.mjs` is the check, per file against the base commit: the old lines outside the declared redrawn ranges verbatim and in order; every expression the old markup evaluated (handlers, guards, conditions, the collection a list is drawn from, formatting calls) present in the new file; every line that touches data, the clock, maths, a format or a permission present; each loss listed with its reason and a `mustContain` for where its figures went; and a branch-wide allow-list that no document builder, engine or snapshot is on. Copy it for such a screen, and run a negative control before trusting it — as first written it had four faults of its own. A dialog that must stay open while it works and show its failure is a `Dialog`, not `ConfirmDialog`; a select whose `onChange` carries logic is `NativeSelect`, not the Radix `Select`, whose `onValueChange` would rewrite the handler. `node design-harness/flows-batch3.mjs` is batch 3's clicks, each ending by proving it sent no write or RPC.
- **Primitives for the legacy shapes:** `PageHeader` for the gradient header cards, `DataTable` for hand-built tables (inline edit fits in `cell`), `Tabs` for filter-button rows, `Badge` with a word and an icon for a status, `KpiCard` for a headline figure, `Alert` for every tinted message box, `Sheet` for a form, `ConfirmDialog` for `ConfirmationModal type="confirm"` and `MessageDialog` for its `success` / `error` / `info` types — both keep that component's contract exactly (confirm and OK call `onConfirm()` then `onClose()`, unawaited). Do not edit `ConfirmationModal` itself; a dozen legacy screens still use it. A `<select>` whose `onChange` reads `e.target.value` or whose `required` guards the form is logic: move it with `NativeSelect` (the browser's select in the design-system frame), not the Radix `Select`, and the handler stays byte for byte.
- **Layout in classes.** `grid-cols-1` on every grid wrapper — a bare `grid` sizes its track to the widest child's min-content, and a tab row alone pushed Fahrzeuge past 375 px. A `DataTable` with row actions needs tighter column padding below `sm`: on a touch screen the icon buttons are 40 px and the default `px-4` pushed the delete button off a 375 px phone. A text field inside a table cell needs `size={1}`, or its 20-character natural width does the same.
- **A figure whose load failed is not shown.** An empty list and a total of 0,00 € are claims; when the read failed, show the error state instead. **A screen whose logic has no failure state gets exactly one, and nothing else** (decided for batch 2, 22.09.2026): a `loadFailed` `useState`, cleared where the load starts and set in the existing catch, and those lines are the only ones a proof may list as added. Beside a zero, it catches the worse case — a failed load for a new month that leaves the **previous month's** rows under the new month's name (Abrechnung, and Bargeldbestand on a month change). Withhold the export while it is set too. A screen reading through `useDatabase` gets no failure from the hook's reads — it falls back to local storage, which nothing writes — and learns of a failed connection only from its `isConnected` (batch 1b's pages read it).
- **Prove it with a script, not a diff read by eye.** `design-harness/prove-batch2.mjs` is the tool to copy: per file, the base's logic block against the new one line by line after removing exactly the listed added lines; every expression the old markup computed inline (a sum, a hint, a handler) as a `carried` snippet that must appear verbatim in both; and a `verbatim` block for markup that must not move at all. Give it a negative control — change one constant, watch it fail. For a screen with an export, `design-harness/exports-batch2.mjs` downloads it in the harness from the base (`--root`) and from the branch and compares the cells. `design-harness/identity-proof.mjs` (batch 1b) is the generic version with no list to maintain: per file, the logic region against a base ref line by line, and every inline `onX={…}` and every call the old markup made to something the logic declares, required verbatim in the new file.
- **Check it rendered, with a touch pointer at 375 px.** `design-harness/` renders the production screens inside the production `AppLayout` on invented data: its own Vite config swaps `src/lib/supabase.ts` (an in-memory store) and the Auth, SuperAdmin, Plan, CompanySettings and `useCompanyScope` hooks at module resolution, so nothing in `src/` changes. A new batch keeps its rows in a `fixtures-batchN.ts` of its own and its shot list in `shots-batchN.mjs` (which `capture.mjs --batch batchN` loads), adds one line each to `fakes/supabase.ts` and `main.tsx`, and writes a `flows-batchN.mjs` that clicks every write and refusal, and can check what each wrote in `window.__harness.writes` — separate files, because batches are built in parallel and meet in these. The frame batch is `design-harness/applayout/`, and it registers the three unconverted screens the harness had no route for (`/overview`, `/benachrichtigungen`, `/werkstatt`) so the frame can be judged around a legacy page. **`--root` swaps the whole harness, not just `src/`** — `configFile` is read from that root — so a before set from a base checkout needs this batch's harness files copied into it and a `node_modules` junction; `scenario.ts` also falls back to Fahrzeuge for any screen name it does not know, which is why a new batch reads `screen` from the query string itself. `settle()` waits for `window.__harness.answered > 0`, so a shot of a screen that issues no query hangs for 180 s. A `DataTable` row with several 40 px actions does not fit 375 px beside two columns: move a column into the first cell below `sm`, and size a grid of actions with `grid-cols-[auto_auto]`, not `grid-cols-2`, whose `minmax(0,1fr)` tracks let the table squeeze them out of their cell. `capture.mjs` waits for the DOM to stop changing, not a fixed pause: `SalariesManagement` commits a frame of stale calculations before its effect recomputes them. **A fake re-exports its real module, so the resolver must never redirect a URL request** (Vite resolves those with `<root>/index.html` as the importer): redirected, a fake re-exported itself, every export it does not redefine was missing, and the harness did not boot — why batch 1b's captures stalled at their first shot. A run warms the server on a thrown-away page, caps each shot and retries a failed one once; `--only a,b` takes one screen at a time. Take the before set from a `git worktree` of the base with `--root`, so both sets share one harness and one browser. `capture.mjs` launches Chrome with `--lang=de-DE` (an English Chrome writes `mm/dd/yyyy` in a date field whatever the page's locale) and takes the 375 px shots as a touch phone. **Batch 4 has a harness of its own**, `design-harness/batch4/` (`npm run harness:batch4`, `harness:batch4:capture`, `harness:batch4:flows`), because its screens render before a session exists and other batches were editing the shared one at the same time: it swaps AuthContext's hook with one whose `signIn` answers each refusal, replaces `window.fetch` so the edge functions (`otp-*`, `manage-users/*`, `company-signup`, `oauth-account`, `/auth/v1/settings`) answer from the scenario while the screens' own fetch calls stay as they ship, records every write in `window.__harness.writes`, and draws the real staging banner with `?env=staging`. It carries its own copy of the rule above (its resolver never redirects a request whose importer is `index.html`), its own `cacheDir` (a shared `node_modules/.vite` behind a junction is rebuilt by every harness that touches it), `lucide-react` pre-bundled (unbundled it is some 1,500 requests per cold page), and `server.fs.allow` naming the real path of `node_modules`, or a linked checkout renders without Barlow.
- **Proof, as a script (batch 4).** `design-harness/batch4/logic-identity.mjs` does the substring check per file against the merge-base, from a list of blocks named by their first and last line, plus two checks the substring cannot make: every call the old file made (`signIn(`, `fetch(`, `navigate(`, `supabase.from(`…) is extracted with its full argument list and must be in the new file, and every *behaving* JSX attribute (`required`, `disabled={…}`, `onClick={…}`, `type="email"`, `value={…}`…) must be too, because those live in markup and a substring of the logic never sees them. An attribute that moved on purpose is listed with its reason; the script also fails if App.tsx, the four contexts, `src/lib` or `src/hooks` changed at all.
- **Two traps batch 4 found.** A legacy `<button>` with no `type` inside a `<form>` **submits it**, and the design-system `Button` defaults to `type="button"` — so a straight swap silently changes behaviour; keep `type="submit"` where the old button had none (PlanSelection's discount buttons inside the Google registration form do, and that is a recorded defect). And `Field` wires its label only into `Input`, `NativeSelect` and `SelectTrigger`; a raw `<textarea>` or `<input>` inside it needs the same `id` on both, or the label points at nothing. (Batch 4's two selects, the Benutzer role and Einstellungen' drivers per car, are batch 3's `NativeSelect` since the rebase.)
- **The style ratchet.** `scripts/style-ratchet.mjs` runs in `npm run build` after the typecheck ratchet and counts, per file under `src/`, inline styles (`style={…}` and imperative `el.style.x =` writes) and hard-coded colours (hex, `rgb()`/`hsl()` with a number, Tailwind palette classes such as `text-green-100` or `bg-white`, quoted `'white'`/`'black'`); the rules and their tests are `style-ratchet-core.mjs` and `style-ratchet.test.ts`. A file above its entry in `style-baseline.json` fails the build, a file below it fails too and asks for `npm run styles:update`; per file, so a converted screen cannot pay for a regression elsewhere. A converted screen is at zero and the test file pins batch 1 there. Like the typecheck ratchet it races with parallel PRs: rebase, run `npm run styles:update`, and read the diff before merging.
- **Contrast across the seam.** `tokens.contrast.test.ts` keeps two blocks for Phase-2 foregrounds on a **legacy** background, and both are still real now that `AppLayout` has moved — neither was deleted, because a pair is removed when nothing renders it, never to make a test pass. `ON_LEGACY_PAGE` (on `--bg-base`) was written for the company frame and is now about **`AdminLayout`**, which still paints `--bg-base` under screens built from the design system: the Team roster, the Protokoll, the settings editors. It retires when AdminLayout moves. `ON_LEGACY_SURFACE` (on the legacy card `--bg-surface`) is unchanged and is not the frame's at all — it is the one-time-code block on Mein Konto, whose card `AccountPage` paints itself, and Mein Konto is one of the six unconverted screens. A new combination goes into one of those or into `PAIRS`. Colours no token owns but a converted screen draws (the staging banner, Google's button) are measured from the component's own source by two `.exec()` regexes that take the **first** `background: '#…'` and `color: '#…'` in the file, so changing either there — or adding an earlier hex, or using double quotes — fails the test. `EnvironmentBanner` is therefore left alone: the staging banner is not a child of this frame anyway, it is fixed to the viewport above the router.

### `fahrtenbuch_trips` is append-only by design

A DB trigger (`protect_fahrtenbuch_immutable_fields`) raises an exception on any UPDATE to `trip_date`, `start_time`, `end_time`, `duration_minutes`, `car_id`, `car_identifier`, route/description, all amount columns, `raw_data_json`, `original_driver_*`, `import_id`, `company_id`. Only the `assigned_driver_*` / `assignment_*` columns are mutable, and **there is no UPDATE RLS policy at all** — every write must go through an RPC. Trips with `is_canceled = true` must never be reassigned or counted.

This constraint shapes the whole planning system: it is why planning is computed entirely in memory and committed in one apply step, and why time corrections in the historical wizard are stored as separate `historical_time_adjustments` rows rather than edits.

**Import facts (`20260922100000`, Fahrtenanalyse slice A).** Since that migration the trigger also protects `source_status`, `is_canceled` (both already did) and eleven columns written once at import: `start_at`/`end_at`/`time_zone`/`time_source` (the ride's instants, read from the source's start and end in Europe/Berlin, NULL with `time_source` `missing`, `unparsed` or `ambiguous` when they cannot be read — never guessed, and never trip_date plus a fixed 24 hours), `trip_status` (`completed`/`cancelled`/`unknown`, tied by a check to `is_canceled`), `needs_review`/`review_reasons`, `currency`/`currency_source` (EUR, `assumed`) and `source_row_key`/`source_row_key_basis`. `trip_date`, `start_time` and `end_time` keep their old meaning: `trip_date` is the file's "Datum der Fahrt", which the Uber export dates a day early for a ride starting just after midnight — **`start_at` is the ride's real start; read it for anything new.** The browser half is `src/utils/fahrtenbuchImportParser.ts` and the SQL half the `app_private.fahrtenbuch_*` helpers; the parser's test reads the migration and fails when the two part. The same file is refused per company (`fahrtenbuch_imports.file_sha256`), and so is the same ride (`source_row_key`, unique per company where set). A row the file left incomplete is stored and flagged, not dropped, and no date is invented: a row with neither a "Datum der Fahrt" nor a dated start cannot be stored while `trip_date` is NOT NULL.

### `app_private`: state the browser must never reach

PostgREST serves only `public` and `storage`. Tables that hold security state live in `app_private` (since `20260915100000`): `otp_challenges`, `otp_send_events`, `pending_signups`, `platform_login_verifications`, and `pending_oauth_signups` (since `20260916100000`). Nobody the API authenticates as has USAGE on the schema — not `anon`, not `authenticated`, not `service_role` — so the only way in is a `SECURITY DEFINER` function in `public` whose EXECUTE is granted to the role that calls it. (`postgres` does have USAGE, through `pg_read_all_data`, and reads the tables; it can call none of the functions.) The platform tables of phase 3 live here too, see *Platform staff, capabilities and the audit log* above. Four rules for anything added there:

- **Revoke from `PUBLIC, anon, authenticated`**, not just `authenticated`. Supabase's default privileges grant EXECUTE on every new `public` function to `anon` too; `20260911120000_redeem_discount_code_rpc.sql` missed that, so do not copy its grant block.
- **A new `app_private` object needs its own REVOKE.** EXECUTE-to-PUBLIC on new functions is a built-in global default and cannot be revoked per schema. Missing USAGE is what keeps callers out; the REVOKE is the second wall.
- **`LANGUAGE plpgsql`, `SET search_path = pg_catalog, public`, `app_private.*` and `auth.*` schema-qualified.** plpgsql resolves `auth.sessions` at call time; the RLS test database only gets GoTrue's tables when a test stubs them.
- **Outcomes are return values, never exceptions.** `otp_verify` counts the attempt before comparing the hash; raising on a wrong code would roll that count back and make the five-attempt lock worthless. A broken argument contract raises `22023` with a fixed message, and no function returns `SQLERRM`. The exception is a refusal that must write nothing: `oauth_signup_create_company` raises one SQLSTATE per reason in class `OA` (the table is in `20260916100020`), and its caller maps the code, never the message.

Each OTP migration ends with a `DO` block that fails the release: the schema file if `anon`, `authenticated` or `service_role` can reach `app_private` or any table in it, the RPC files if any function they created is executable by `anon`/`authenticated` or lacks a pinned `search_path`. `app_private.platform_login_verified(user_id, session_id)` has no grant for anyone, and nothing calls it: platform sign-in stays an address and a password (the owner's decision of 16.09.2026), so `is_user_super_admin()` does not ask it. The same ownership rule holds for every `app_private` helper: a caller must be a `SECURITY DEFINER` function owned by a role that already holds USAGE on `app_private` and EXECUTE on it — in practice `supabase_admin`, which runs the migrations (see *Platform staff* above for functions still owned by `postgres`). The limits (10 min validity, 5 attempts, 60 s cooldown, 5 codes per address and 20 requests per IP per hour, 12 h platform verification) are `CONSTANT`s in the one function that enforces each.

Signup is code-confirmed: `signup_create_company` writes the company, an owner profile in status `pending_invite` and a `pending_signups` row in one transaction; `signup_complete` activates the owner and redeems the discount code only after the code is entered. `purge_unverified_signups` and `signup_discard_unverified` delete **only** accounts in `pending_signups` — legacy unconfirmed production accounts were never written there and no job can reach them. `auth.users.email` is copied to `user_profiles.email` by the `sync_user_profile_email` trigger, whatever changed it.

Google signup (plan step 1.6) is the second way in; nothing calls it until PR B turns it on. GoTrue inserts the account itself, and the `AFTER INSERT` trigger `mark_pending_oauth_signup` on `auth.users` records it in `app_private.pending_oauth_signups` when the row's `raw_app_meta_data` names provider `google`, which GoTrue v2.170.0 writes only for a new external account. The trigger runs inside GoTrue's transaction, so it is one `INSERT … ON CONFLICT DO NOTHING` with no lookup that could raise; keep it that way, or every Google sign-in fails. **A new account has no `user_profiles` row at all until its company is written, and no trigger writes one.** `public.handle_new_user()` exists and still reads as if it did — a company-less `viewer` in `pending_invite`, last rewritten in `20260908103000` — but nothing invokes it: `auth.users` carries exactly two triggers, `mark_pending_oauth_signup` and `sync_user_profile_email`. A trigger *was* once intended (the chain creates `on_auth_user_created`, last in `20260402100619`), and it is absent for the reason under *Known defects*: the live schema was restored from a `--schema=public` dump, which carries a `public` function but no trigger on `auth.users`. Nothing needs it — `app_private.signup_insert_company` writes the owner's profile itself with `INSERT … ON CONFLICT (user_id) DO UPDATE`, so both `signup_create_company` and `oauth_signup_create_company` write it whether or not a row exists, and `manage-users` upserts on `user_id` too. Two comments still assume production has it, and neither is evidence: the header of `20260916100020` ("handle_new_user gave it a company-less viewer profile in status pending_invite") and `tests/rls/oauth-signup.sql`, whose prelude **creates** the trigger, so the RLS kit cannot notice its absence. Adding it is the owner's decision, not a side effect of a bug fix: it would write a profile into both signup RPCs' transactions. **So every gate that reads the profile must treat "no row" as "not yet registered", never as "nothing to do"** — `needsCompanyRegistration` (`src/lib/googleAccount.ts`) began `if (!user || !profile) return false`, which let the owner's own Google signup into the tenant router with no company, where every query asked for `company_id` null and the screen filled with `invalid input syntax for type uuid: "null"`. `oauth_signup_create_company` writes the password signup's rows through `app_private.signup_insert_company`, the one place for the trial length, slug and owner role, with the owner `active` and the discount redeemed at once. `oauth_session_reconcile` cancels a never-approved password signup that GoTrue has just linked to Google, and accepts a pending invitation. `oauth_signup_discard` and `purge_abandoned_oauth_signups` delete only marked accounts with no company that are not platform staff. Every signup path asks whether an account is staff through `app_private.oauth_account_is_platform_staff`, which since `20260916110010` reads `app_private.platform_staff` (any row, a disabled one included): the Google functions, and `signup_create_company` and `signup_discard` too. Change that rule there, and write the company through `app_private.signup_insert_company`, never through a copy of it. **Platform staff never sign in with Google** (owner decision, 16.09.2026): their sign-in stays email and password. The database already refuses or ignores them in every `oauth-account` action (register raises `OA005`, reconcile answers `platform_staff` before it changes anything, discard and the purge delete no staff account), and hiding Google from staff in the UI is PR C's. **The server-side half is built since `20260919130000`** — see *A platform capability requires a password-backed session* below.

A new RPC needs no `NOTIFY pgrst` and no restart of `rest` (which `deploy.sh` never recreates): the `supabase/postgres` image installs the `pgrst_ddl_watch` event trigger, which tells PostgREST to reload its schema cache after every DDL statement.

## The planning pipeline (the core of the product)

Entry point `src/pages/CompanyPlannerPage.tsx` branches on `planningMode` into three workflows: `new_month` (the standard pipeline), `historical_reconciliation` (Brutto-Gehälter mode), and `hist_working_hours` (Arbeitsstunden block-engine mode).

### Standard monthly planning

Phases 1–4 are **pure, in-memory, zero DB I/O**. Nothing is written until "Plan anwenden".

| Phase | File | Entry point |
|---|---|---|
| 1 — build vehicle blocks from trips | `utils/monatsplanungPhase1.ts` | `buildPhase1VehicleBlocks` |
| 3 — assign drivers to blocks (greedy + repair) | `utils/monatsplanungPhase3.ts` | `assignBlocksPhase3` |
| 4 — build change set + consistency check | `utils/monatsplanungPhase4.ts` | `buildChangeSet` |
| 5 — apply | `components/MonatsplanungAssignmentPreview.tsx` | `handleApply()` |

`utils/monatsplanungRepairPass.ts` (`repairFinalOverlaps`) and `utils/driverNoteValidation.ts` are pulled in by the preview component during phase 3/4 review.

Phase 3 splits rejection reasons into **hard** constraints that can never be bypassed (`wrong_weekday`, `driver_overlap`, `vehicle_switch_buffer_violation`, `one_vehicle_per_day`, `note_constraint`) and **bypassable** ones a manual exception can override (`outside_working_time_window`, `daily_max_exceeded`, `monthly_max_exceeded`). Preserve that distinction — the bypassable ones are persisted as flags on the trip and audited in `monthly_planning_manual_exceptions`.

Phase 5 writes `company_planning_runs`, batch-updates trips via RPC, inserts manual exceptions, and stores an `apply_summary_json` whose `updated_trips` count is re-verified later during finalization. **One applied run per company/month/year**; a second apply offers "Bestehende Planung ersetzen" via `replace_monthly_planning_run`, which archives the old run.

Downstream of apply: `MonatsplanungStundennachweisPreview.tsx` (time records, Lohnart computation, Gehaltsabweichung, Transfer Analysis) and `FinalizePlanningModal.tsx` (pre-flight checks, then document generation).

### Finalization is a hard gate

`FinalizePlanningModal.tsx` runs ~10 blocking pre-flight checks (run status is `applied`, trip count matches `apply_summary_json`, no duplicate trips, every non-canceled trip has a driver / block / start+end time, max 3 Schichten per driver per day, no short vehicle switch, driver summary builds). **There is no override.** Documents are downloadable only after all checks pass. Applying a trip transfer afterwards sets `planning_finalizations.is_stale`, forcing re-finalization.

The `Fahrzeugwechsel zu kurz` check compares absolute millisecond timestamps and skips negative gaps — an older `HH:MM`-string implementation produced nonsense negative gaps across midnight. Keep timestamp arithmetic; do not regress to time-of-day math.

### Historical Arbeitsstunden mode — the block engine

`HistoricalWorkingHoursWizard.tsx` (~11.7k lines) drives a deterministic block pipeline. **The engine lives in `utils/historicalWorkingHoursCleanEngine.ts`** (~2.8k lines, 55 exports) — `buildVehicleBlocksForHistoricalWorkingHours`, `assignRegularDriversToVehicleBlocks`, `assignSurplusBlocksToInhaberWithoutTimeChange`, `shiftOverlappingInhaberBlocks`, `buildFinalBlockAssignmentSnapshot`, `validateHistoricalWorkingHoursExportReadiness`, `computeLohnartSeconds`, `getGermanNationalHolidays`.

The wizard also pulls in three sibling modules: `historicalRowLevelEngine.ts` (row-level Arbeitsstunden engine + export overlap validation), `historicalWorkingHoursFahrtenbuchExport.ts` (final XLSX build + overlap validation), and `historicalWorkingHoursStundennachweisPreview.ts`.

> **Do not trust `Docs/TECHNICAL_REFERENCE.md` here.** It attributes the block engine to `ManualTimeCorrectionPanel.tsx` and to `historicalReconstructionSolver.ts`. Both were dead code and have been deleted. The `Clean Engine` module above is the live implementation.

Two rules still hold:

- **Overlap checks are ride-level and absolute.** Build intervals from `date-midnight-ms + secondOfDay * 1000`, never from a bare `HH:MM:SS` string (which parses to `0`). Cross-midnight rides depend on this.
- The snapshot produced by `buildFinalBlockAssignmentSnapshot` is the **sole** source of truth for Stundennachweis PDF rows, Lohnart actuals, export validation, name validation, and the Fahrtenbuch XLSX driver overlay. Do not add a second source.

Overlaps that already exist in the raw imported data are tracked separately and surface as amber "Originaldaten-Warnung" that does **not** block export. Only overlaps the app itself created are blocking errors.

The Brutto-Gehälter mode (`HistoricalReconciliationWizard.tsx`) is a different pipeline — it uses `utils/shiftBlockEngine.ts`, not the clean engine and not the reconstruction solver.

## Domain rules that are easy to break

- **Business week ownership** (`utils/weekCalculations.ts`): a week belongs to the month containing its **Monday**. April 1st falling on a Tuesday belongs to March. Every monthly aggregation depends on this.
- **Salary**: `(Umsatz + Aktionen) × driver.salary_ratio + Trinkgeld × 100%`. Bargeld and Trinkgeld are pass-through and never count toward company profit.
- **Abrechnung**: weekly balance = cash collected − cash expenses; positive means the driver owes the company.
- **Tankenquote** uses only receipts with Kategorie `Tanken` for that driver and period, and only the resulting percentage is displayed.
- **Night/Sunday premiums**: Lohnart `1500` (25% steuerfrei) and `1501` (40% steuerfrei) are mutually exclusive — `1500 = nightSec − night0to4Sec`, `1501 = night0to4Sec`. Never double-count.
- **Schicht compression** (max 3 shifts/day) is display- and export-only. It must not alter stored minutes, premium buckets, or Brutto figures.
- **Ausgleichsstunden** exist only in the Stundennachweis, always as Lohnart `1000` with no premium. They must never create trips or touch `fahrtenbuch_trips`, and must never appear in the Fahrtenbuch.
- **Belegnummer is always system-generated** (`BEL-{timestamp}-{random}`, collision-checked). OCR output must never overwrite it.
- **Gehaltsquittung (cash salary receipt) is a ledger entry** (`supabase/migrations/20260914140000_salary_cash_receipts.sql`). `confirm_salary_cash_payment` writes the receipt (`GQ-YYYY-NNNN`, gapless per company and year), its `salary_payments` row (`source_type = 'gehaltsquittung'`) and an outgoing `cash_movements` row in one transaction; it is idempotent on `request_id` and refuses more than the balance it reads under lock. **The `YYYY` in the number is the year of the *salary*, not of the payment** — `business_year`, the business year of `period_start`, the same value the row already stored (owner decision 17.09.2026, `20260919160000`; it was the payment year until then). So the counter is keyed on that year, two receipts issued on one day for salaries of different years take numbers from different counters, a company's numbers are no longer in the chronological order of its payments, and a late payment appends to a closed year's sequence. Receipts issued before that migration keep the payment year and are **never** renumbered, so both conventions exist in the history; `business_year` on the row is right for either, and is what a report groups by. `void_salary_cash_receipt` deletes the payment and books the cash back on the day of the void; the receipt stays, marked `voided`. A trigger refuses any direct edit, delete or forged insert of a receipt's payment. Due is `COALESCE(netto_salary, amount_due)`; the weekly "Bar zurück" counts as paid and never moves cash. Every writer locks the salary row `FOR NO KEY UPDATE`, never `FOR UPDATE`: a payment's foreign-key check holds a key share on the salary, `FOR UPDATE` conflicts with it, and two concurrent payments deadlock. The browser mirror computes in integer cents (`utils/money.ts`, `utils/salaryCashReceipt.ts`) and walks the same scenario as `tests/rls/salary-cash.sql`. **The reading side is `utils/cashLedger.ts`**, and `BargeldbestandPage` and the Overview's cash panel (`calcCashSummary`) go through it: the balance is `Bargeld − Belege − (Gehaltsquittungen − Stornos)`, in integer cents, and because a Storno is booked on the day of the void, a receipt paid in one month and voided in the next lowers the first and raises the second rather than cancelling inside either. Nothing on the reading side touches `salary_payments`, which is what keeps "Bar zurück" — paid, but never taken from the till — out of the balance by construction. `tests/staging/cash-ledger-parity.sql` is the read-only comparison behind that, and it proves less than its own summary suggests: staging holds 0 `cash_movements`, 0 `salary_cash_receipts` and 0 `salary_payments` of `source_type = 'gehaltsquittung'` across 19 companies, so every period it compared carried a third term of exactly zero — it showed the two formulas agree where there is nothing to disagree about, never exercised the divergence, and its sensitivity check is a hypothetical computed in SQL rather than against the TypeScript that ships. The check that does exercise it is seeded, run immediately after a staging deploy and on the e2e test company only, never a real customer's: one salary, `confirm_salary_cash_payment` of 300,00 € in month M and `void_salary_cash_receipt` in M+1, then both months' Bargeldbestand read against the script scoped to that company — M down exactly 30000 cents with the payout card at 300,00, M+1 up 30000 with the card at −300,00. **Both ledger tables used to be readable by the owning company only** — `cash_movements` and `salary_cash_receipts` were SELECT-policied `company_id = get_user_company_id()` with no platform branch, unlike `income` and `receipts`, so platform staff inside a customer read that customer's Bargeld and Belege and none of its movements. Since `20260917130000` they carry the same SELECT shape as every other business table, and since `20260917140000` that shape's platform branch is `false`, so a staff account reads them only inside an open context on the company, and the owning company's own read is state-gated like the rest. An empty set is still indistinguishable from "no payouts", so both reading screens ask `cashLedgerInScope(...)` (`utils/salaryCashReceiptFlow.ts`) before making any claim. **3.3 did not lift that guard; it narrowed it.** The ledger is in scope for the caller's own company — the `receiptScope(...) === 'own_company'` the Gehaltsquittung screens use — **or** for a reader holding `business.read`, which is the policy's own platform branch: the read is granted by capability, not by staff status, and `platform_reads_company_data()` was `platform_can('business.read')`, which `billing` does not hold — and is `false` for every role since `20260917140000`, so outside a context nobody reads them. A billing account therefore still reads no movements and must still not be shown a till that looks complete, so the guard remains for it and for anyone else outside their own company. Out of scope the Bargeldbestand drops the payout card, keeps the older `Bargeld − Belege` label and says why, the Excel dump carries the same caveat, and the Overview hides its payout line. **Writing them is still nobody's**: `authenticated` holds SELECT and nothing else, and the three RPCs are the only writers — and since `20260917130000` those three resolve the caller's company with `get_active_company_id()`, so a suspended, rejected, unapproved or unsubscribed company, and a deactivated, suspended or inactive account, are refused with `Keine Berechtigung` (`not_authorized`) instead of writing a receipt with the token they already hold. `GehaltsquittungModal` keeps one `request_id` per payment until the database answers (`nextAttempt` in `utils/salaryCashReceiptFlow.ts`). From the moment the request leaves, the attempt is also written to the tab's `sessionStorage`, so closing the dialog or reloading the tab resumes that same id instead of starting a second payment; a definitive answer clears it, and while it is unanswered the dialog offers only a retry and a close that says what is still open. What that does **not** cover: another tab, another browser, or storage the browser refuses — there the receipt list is the check before a payment is entered again. The receipt's text is built in `utils/salaryCashReceiptDocument.ts`, German in both languages, and once confirmed it prints the row the database stored, not the preview. **The sheet names the salary's `Abrechnungsmonat`** beside its Zeitraum (owner decision 18.09.2026), because after the numbering change the `GQ-YYYY` is the only place the salary's business year appears and a January period numbered `GQ-2025-…` otherwise reads as an error: it is the stored `business_month` / `business_year` pair, read through `RECEIPT_COLUMNS`, and **only the preview derives it**, with `businessMonthOfPeriod()` → `getBusinessMonth()`, the browser twin of `get_business_month()` — whose months count from **0** where the column counts from 1, so the `+ 1` lives in that one function. Recomputing it for a confirmed receipt would let a later change to the calendar rule reprint an issued document under a month other than the one it was numbered by. The receipt list carries the same column, but it is a screen and not the document, so its header follows the UI language. Each signed copy is uploaded under a new name, so replacing one moves the receipt's pointer and never overwrites the earlier file. **A platform support session issues, voids and signs nothing here, permanently** (owner decision 18.09.2026): `receiptScope()` answers `other_company` inside a context, so both Gehaltsquittung screens refuse — because the receipt attests to a physical handover of cash that no platform agent witnessed, which is a question of attestation that no audit log can answer, and not of traceability (the actor *is* recorded, in `confirmed_by`, `voided_by` and `cash_movements.created_by`). Do not reopen it now that 3.4c's write-audit triggers (`20260920110000`) record such a call row by row: that makes it traceable, not permitted. **The database refuses it too since `20260921110010` (slice 3.13a)**: each of the three RPCs raises 42501 with HINT `platform_session_not_allowed` for a caller inside a platform context, in either mode, before it reads an argument, takes a lock or draws a number. The condition is "a company, and no membership" — `v_company` is the function's own `get_active_company_id()`, which answers a company to an account with none of its own only from an open context — so it needs no new helper and no grant for the functions' `postgres` owner. The bodies were changed from the catalogue (one block spliced in front of the authorization check, which must match exactly once), like 3.3's and the GQ-year rewrite, and the migration's self-check re-asserts every load-bearing fragment of each old body. `receiptScope()` stays the first wall, so the screens say why before a request is sent; the browser maps the new reason to the same sentence as `company_mismatch`.
- **A driver can hold salary rows with overlapping periods.** `unique_driver_period` is only `UNIQUE (driver_id, period_start)`, so a calendar month beside a business month passes it; staging's copy of production has 25 such rows in one company. The receipt RPC refuses such a salary (`overlapping_salary`) until the owner decides how to merge them, and the unique index on driver and period waits for the same decision.

## Known defects and sharp edges

- **`supabase/migrations/` cannot bootstrap a database.** `companies`, `drivers`, `receipts` and `saved_stundennachweise` are only ever `ALTER`ed and RLS-policied — they have no `CREATE TABLE` anywhere in the chain. The live schema was partly created outside version control. A fresh Supabase project will not come up from migrations alone.
- **Two block-building pipelines still disagree.** `monatsplanungPhase1.ts` chains rides into a block across gaps up to `VEHICLE_BLOCK_GAP_MINUTES = 60`; `shiftBlockEngine.ts` (the Brutto-Gehälter pipeline) uses `BLOCK_SEPARATOR_GAP_MINUTES = 90`. The same month therefore produces different blocks depending on which mode processed it. The name collisions that used to compound this — `MIN_VEHICLE_SWITCH_BUFFER_MINUTES` defined as both 60 and 30, plus duplicate `buildVehicleBlocks` / `parseFullDatetimeMs` / `getHolidaysForYear` — are gone with the dead modules that held them; no exported name is defined twice any more.
- **Two holiday tables still disagree**, and the golden-master tests pin the difference: `getGermanNationalHolidays` (clean engine) counts Ostersonntag as nationwide, `getHolidaysForYear` does not. See the test section above.
- **Transfer application is not atomic.** `MonatsplanungStundennachweisPreview.tsx` (~line 3204) applies a multi-trip transfer by looping `reassign_fahrtenbuch_trip` once per trip. A mid-loop failure aborts and leaves the transfer **partially applied** — the error message even reports "X von Y Fahrten wurden aktualisiert". There is no rollback.
- **Who may call an edge function is decided in `supabase/functions/main/index.ts`, and nowhere else.** Self-hosted, there is no dashboard `verify_jwt` setting; the router verifies every bearer token against `JWT_SECRET` and `PUBLIC_FUNCTIONS` names the exceptions, each with its reason. A function added later that must be reachable without a session has to be listed there, in a commit. Note what that check is and is not: it proves the caller holds a token this stack signed. It is not authorization — each function still loads the caller's profile and checks role and tenancy itself (the `assertSameCompany()` pattern in `manage-users`), and it is not rate limiting, because the anon key that admits `company-signup` ships in the browser bundle. The router also decides **what each function can see**: `FUNCTION_ENV` lists the environment variables every worker receives, and a function without an entry answers 404 and is never started. `JWT_SECRET` stays with the router, `SUPABASE_DB_URL` is not set at all any more, and until this list existed every worker got the whole container environment. A new function, or a new variable for one, needs its line there as well as in `deploy/docker-compose.yml`. Measured in the staging container: a worker sees exactly its list plus the runtime's own `SB_EXECUTION_ID`. `otp-request` and `otp-verify` are public because signup, "Passwort vergessen" and invitations happen before a session exists; their `email_change` and `platform_login` purposes verify the bearer token inside the function. `platform-staff` is not public, which is why the codeless email change of 17.09.2026 was added there as a route rather than as a function of its own: the entry it would have needed here, and in `deploy/docker-compose.yml`, is the reason to prefer a route on an authenticated function every time. `oauth-account` (Google sign-in: `reconcile`, `register`, `discard`) is deliberately not public: it asks GoTrue whether the caller's session still exists, and every `oauth_*` RPC it calls as `service_role` receives that caller's user id, never one from the body.
- **Every new function is executable by anon until a migration says otherwise.** Supabase's default privileges grant EXECUTE on each new function to PUBLIC, anon, authenticated and service_role.
  - **"service_role only" means revoking all three.** `20260911120000` missed anon, which leaves the function's own guard as the only barrier.
  - **That guard must not compare a value that can be NULL.** `IF auth.email() != '…' THEN RAISE` let an anonymous caller read every account through `list_users_for_admin()` until 15.09.2026 (`20260915110000`). Write `IS DISTINCT FROM`, or check `auth.uid() IS NULL` first.
  - **A SQL helper that selects a single row returns NULL when no row matches.** `SELECT COALESCE(is_super_admin, false) FROM user_profiles WHERE user_id = auth.uid()` looks NULL-safe, but anon, the service role and a signed-in account without a profile have no row to coalesce. `is_user_super_admin()` therefore answered NULL, and `IF NOT is_user_super_admin() THEN RAISE` let the anon key into `create_user_profile_manual` until 15.09.2026 (`20260915130000`). Wrap the whole subquery: `SELECT COALESCE((SELECT … LIMIT 1), false)`. A policy denies on NULL just as on false, which is why nobody noticed; `NOT`, `CASE`, `COALESCE` and `IS` tell the two apart.
  - **Check it in the migration's self-check** with `has_function_privilege('anon', …)`.
- **`extract-receipt` still spends `ANTHROPIC_API_KEY` on any request that carries a valid token**, and does no role or tenant check of its own. It is called by nothing (see the OCR entry below), so the exposure is bounded by the router — but if it is ever wired up, it needs its own checks and a spend limit first.
- **Two OCR implementations, one live.** The UI uses client-side Tesseract (`utils/receiptOcr.ts` → `ReceiptModal.tsx`). The `extract-receipt` edge function (Claude vision via the Anthropic SDK) is called by **nothing**. The claim in `Docs/TECHNICAL_REFERENCE.md` that it "wraps Tesseract" is wrong on both counts.
- **Notifications are built, and inert until a host cron line is installed** (`20260924100000`). The four types `NotificationsPage.tsx` writes to `notification_settings` — `tuev_bald_ablaufend`, `tuev_abgelaufen`, `trial_bald_ablaufend`, `trial_abgelaufen` — are read by the edge function `notify-expiries`. There is still no scheduler in the stack: the job is driven by a host cron line installed by hand like `/etc/cron.d/el-professor-otp` and the audit purge, and **HANDOFF.md carries the line and the dry run to take first**. With no line, nothing is called and nothing is sent; a call with no body, or a body that does not parse, is a dry run, so a mistyped line cannot mail a customer.
  - **The decision lives in one pure module**, `supabase/functions/_shared/notification-core.ts` (no Deno, `npm:` or `jsr:` import, so vitest runs it). `notification_candidates(p_tuev_soon_days, …)` narrows in SQL — `approval_status = 'approved'` and `status IN ('active','trial')`, the hard boundary — and the module does the arithmetic. The windows are the product's own numbers, `TUEV_SOON_DAYS` 60 (`getTuevStatus()` in `src/types/car.ts`) and `TRIAL_SOON_DAYS` 7 (`TrialBanner`), defined once and **passed into** the query so the mail and the screen cannot disagree about the same car.
  - **Both trial types require `NOT subscriptionIsActive(…)`, and that term is the whole paying-customer case.** `companies.status` stays `'trial'` for ever, so a job judging the trial by `trial_end` alone mails "your trial is ending" to a customer who is paying — the defect the browser made twice. The predicate is written twice because the job cannot import from `src/`, and `src/utils/notificationSelection.parity.test.ts` imports both copies and pins them to the same answers. A row that fails there is not fixed by copying one side onto the other: decide against `get_active_company_id()`, then move both.
  - **The subscription terms are deliberately not in the SQL boundary**, and the migration's self-check fails a `notification_candidates` that acquires one: `trial_abgelaufen` is precisely a notification to a company whose access has just lapsed, and a company inside its trial has `subscription_status = 'inactive'` because that is what `signup_insert_company` writes.
  - **The dedupe key is the occurrence, never the day of the run.** `notification_deliveries` is `UNIQUE (company_id, notification_type, target_id, period_key)`, where `period_key` is the date the notification is *about* — the car's `tuev_gueltig_bis` or the company's `trial_end`. So a TÜV that is never renewed is mailed once rather than nightly, a renewed one is a new occurrence and is warned about again, the warning and the expiry are separate occurrences of the same date, and an extended trial is a new occurrence. **The job claims before it sends and never retries:** a crash between the two loses the notification (visible as `mail_sent IS NULL`) rather than repeating it, which is the worse failure, and it is what makes two overlapping runs safe.
  - **`notification_deliveries` is the one business table no client writes, and it carries both context triggers anyway.** SELECT is the ordinary tenant shape; there is no INSERT, UPDATE or DELETE policy and no grant beyond SELECT, and its two writers are SECURITY DEFINER functions granted to `service_role` alone. It still carries `refuse_read_only_context_write` and `record_support_write`, because **the rule is keyed on the policies, not on who writes today**: `tests/rls/platform-contexts.sql` section 14 requires the refusal trigger on every table whose policies name `get_active_company_id()`, and `tests/rls/support-write-audit.sql` section 1 fails a table carrying one of the pair without the other. The first version of this migration reasoned from "no client writes it" and shipped with neither; the kit refused it. Deriving the shape from the tenancy predicate is what stops the next person who adds an INSERT policy from having to re-derive the argument. For the job the pair costs one `current_setting` per statement: `service_role`'s JWT carries no `sub`, so `refuse_read_only_context_write` returns on its `v_uid IS NULL` branch without arming the flag, and section 4b of `tests/rls/notifications.sql` pins that — without it the pair would have written one audit row per notification, every night, with no actor.
  - **Recipients are `selectActivationCodeRecipients`' company branch**, not a second rule: the company's active `admin` profiles that are not platform staff, with a confirmed, undeleted, unbanned account, and nobody when there are none.
  - **The wording is fixed German in `_shared/notification-mail.ts`.** Making it editable from the panel means a `mail.template.*` key, and a key means restating `app_private.platform_settings_problem` with every existing branch character for character — a slice of its own. The five templates `email-layout.test.ts` pins to their exact bytes are untouched.
  - **`notify-expiries` is not in `PUBLIC_FUNCTIONS`, and the router's check is not its authorization**: that check only proves a token this stack signed, which every signed-in customer holds, so the function compares the bearer against `SUPABASE_SERVICE_ROLE_KEY` in constant time itself. It is a function rather than a route because its caller is a cron line with no `auth.uid()`, which every platform RPC would refuse.
  - Still open: nothing in the product *reads* `notification_deliveries` (a "zuletzt gemeldet" panel is a UI-only follow-up), and `cars.status` is not filtered on, because the column has no `CREATE TABLE` in the chain and its domain is unknown — the dedupe bounds an out-of-service car to one mail per expiry date.
- **Outgoing mail goes through Resend over SMTP on port 2587**, configured by `deploy/set-resend.sh`. The VPS provider blocks outbound 465 and 587; Resend's alternate 2587 is STARTTLS. Do not "fix" it to 465 — GoTrue picks implicit TLS by looking for port 465, and that port is closed here anyway. Verified 2026-09-13 end to end through GoTrue's own mailer, not just a direct SMTP login: an invite sent via `/auth/v1/invite` reached Resend and showed `delivered`. Mails use German, El-Professor-branded templates built by `scripts/build-email-templates.mjs` into `public/email-templates/`; GoTrue fetches them from the `web` container. **Edit the generator, not the generated HTML.** Its layout is `supabase/functions/_shared/email-layout.mjs`, shared with the one-time-code mails, and `email-layout.test.ts` pins the five templates to their exact bytes, so a layout change that alters them fails on purpose. The `recovery` template is sent in two situations — a newly invited employee and "Passwort vergessen" — so its copy says *festlegen*, not *zurücksetzen*. One gap remains: the Resend domain was created in region `ap-northeast-1` (Tokyo); an EU region would keep mail processing in the EU, and changing it means re-adding the domain and its three DNS records.
- **The functions send the one-time codes themselves**, through `supabase/functions/_shared/mail.ts`: a small SMTP client on `Deno.connect` that reads the same `SMTP_*` settings as GoTrue. Port 465 is TLS from the first byte, any other port requires STARTTLS, only the host `mailpit` may be plain, and the whole exchange gets 10 s. Probed on 15.09.2026 in a throwaway runtime process inside the staging functions container: plain SMTP to Mailpit delivered with and without AUTH, STARTTLS with `smtp.resend.com:2587` completed against the real certificate and was refused at `MAIL FROM` (530) without credentials, and a send handed to `EdgeRuntime.waitUntil` finished 1.5 s after the response. An authenticated send with production's Resend key was not part of that probe; it is the first check after the release. The client is ours rather than a library: no npm download when a worker boots, no Node-compatibility layer under production mail, and its protocol half (`smtp-core.ts`) is unit-tested against a scripted server. A code is never logged, returned or stored: the database holds only `HMAC-SHA256(OTP_PEPPER, "<challenge_id>:<code>")`, and every limit (5 attempts, 60 s cooldown, 5 per address and 20 per IP per hour) is enforced in the `otp_*` RPCs. `otp-request` answers the three public purposes with one 202 whatever the account's state, never sooner than 1.5 s. `deploy/otp-housekeeping.sh` purges old codes hourly, and unconfirmed signups and abandoned Google signups daily; like the release wrapper, it is installed and scheduled on the host by hand (`/etc/cron.d/el-professor-otp`), and a release does not replace it. `generate-activation-code` mails the code it generates the same way (`_shared/activation-code-delivery.ts`): to the code's `target_email`, otherwise to the active admins of its company whose address is confirmed, otherwise to nobody. The 2-minute validity is unchanged, a failed send never undoes the code, and the response adds `mail_sent` and `recipient_count`.
- **`GOTRUE_MAILER_URLPATHS_*` name an API route, not a screen.** GoTrue appends them to `API_EXTERNAL_URL`, so they must be `/auth/v1/verify`. They were once set to `/auth/callback` — the SPA page the user lands on *afterwards* — which put `https://api…/auth/callback?token=…` in every mail and Kong answered 404. `redirect_to` is what carries the user on to `/auth/callback`. GoTrue's own default, `/verify`, is wrong here too: it lacks the `/auth/v1` prefix Kong routes on.
- **`auth.admin.generateLink` does not send mail, and it creates an account for an address GoTrue does not know.** Both probed against v2.170.0. `manage-users` once used it to "invite" employees and discarded the result, so no invitation was ever sent while the UI reported one. Its only caller now is `issueSession()` in `_shared/otp.ts`, after a verified code: it loads the user by id, refuses unless the address matches, generates a magic-link hash and exchanges it at `POST /auth/v1/verify` with exactly `{type, token_hash}` (any other field is a 400). Never hand `generateLink` an address that has not just been resolved to an existing user. Mail that must go out is a code sent with `issueAndSendOtp()`, invitations from `manage-users` included.
- **A session minted by a link must survive the inactivity check.** `AuthContext` signs out a restored session whose `lastActivity` is missing or older than 20 minutes. A password-reset or invite link creates a *new* session in a browser that usually has exactly that — so every such link used to end in "Link ungültig". A session whose `last_sign_in_at` is under 5 minutes old now counts as fresh. Separately, supabase-js strips the URL hash while it creates the session, so `type=recovery` / `error=` are read into `authRedirect` in `src/lib/supabase.ts` before the client exists; `AuthCallbackPage` reads that, never `window.location.hash`.
- `index.html` builds its share-image URL from `%VITE_APP_URL%`, which Vite fills in at build time; a build without that variable leaves the placeholder in the tag. Favicons, app icons and the 1200×630 share image live in `public/brand/`, cut from the owner's brand board. (Its `lang` attribute is `de` and is kept in step with the chosen language at runtime.)

## Dead code

No dead **files**. 20 unreachable modules (18,063 lines) and the dead `backend/` PHP directory were removed; every file under `src/` is reachable from `src/main.tsx`.

**That claim is per file, and it hides things.** `AutoShiftPlanView` in `HistoricalWorkingHoursWizard.tsx` (lines ~6001–8957, about 2,100 lines with its two algorithms `runAutoShiftPlan` and `runLargestBlankPackingShiftPlan`) is never rendered: the tag appears nowhere, `inhaberAutoShiftResult` is set to `null` at all six call sites and never read, and `onApplyAutoShiftPlan` is a no-op. It sits inside a live file, so the file-level walk passes it. Its German text is deliberately untranslated — a note at line 6001 says so — because keys for text no user can reach are pure cost. Translate it in the same change that makes it reachable, or delete it.

Keep it that way, and check at both granularities. A reachability walk lives at the end of this section's history — rebuild it in a scratch file if you need to check again: start at `src/main.tsx`, follow every static and dynamic import transitively, and anything under `src/` not visited cannot execute. Grepping for a filename is not equivalent, because a module imported only by another dead module still looks used. Within a file, the equivalent question is whether a component is ever used as a JSX tag and whether the state feeding it is ever read.

Deleting it did **not** shrink the bundle — Rollup was already tree-shaking it. What it removes is the far more expensive kind of cost: three of the four competing premium engines, a second `MIN_VEHICLE_SWITCH_BUFFER_MINUTES` with a different value, and several thousand lines that the older docs still describe as the live implementation.

## Repository hazards

- **The docs contradict the code. The code wins.** `Docs/MIGRATION_COMPLETE.md` and `Docs/MYSQL_MIGRATION_GUIDE.md` describe a completed migration to a PHP/MySQL backend that **never happened**. The `backend/` directory and `src/lib/api.ts` they document have since been deleted as dead code; Supabase was always the only backend. `Docs/RLS_FIX_EXPLANATION.md` claims `user_profiles.id` is a `bigint`; the first migration creates it as `uuid`. Confirm every constant, table and RPC name in source before relying on a doc.
- **Status documents travel with every change.** `PROGRESS.md` (progress log, Arabic, for the owner), `HANDOFF.md` (where things stand, for whoever picks the work up), the "Project status" section at the top of `README.md` and the progress table in `el-professor-plan.html` are updated in the same PR as each fix or feature. `README.md` used to hold two concatenated copies of itself; the stale second copy was removed on 14.09.2026, and on 15.09.2026 its developer reference (§1–25) moved to `Docs/TECHNICAL_REFERENCE.md`, which still predates the self-hosted stack in places — the code wins.
- `Docs/` duplicates several root docs byte-for-byte. Editing one leaves the other stale.
- Root-level `*.sql` fix scripts (`FIX_INCOME_POLICIES.sql`, `fix_admin_role.sql`, `apply_salaries_migration.sql`, …) are **not** part of the migration chain. Only `supabase/migrations/` is schema history — with the completeness caveat above.
- Large files to grep rather than read whole: `HistoricalWorkingHoursWizard.tsx` (11.7k), `StundennachweisPage.tsx` (4.0k), `MonatsplanungStundennachweisPreview.tsx` (3.9k), `historicalWorkingHoursCleanEngine.ts` (2.8k).
- `.claude/settings.json` registers a `PostToolUse` hook pointing at `/tmp/cc-agent/57153190/project/.claude/strip-prose.py`, a path from a different machine. It fails silently (`|| true`).
- `.bolt/` is leftover Bolt scaffolding. `vite.config.ts.timestamp-*.mjs` files are Vite temp artifacts and are gitignored.

## Working style for this codebase

Prefer small, targeted, reversible changes. The planning, salary, and reconciliation code encodes statutory German payroll rules that are far more intricate than the code shape suggests, has no test coverage, and produces documents that go to an accountant — a plausible-looking refactor can silently corrupt someone's payroll. When a change touches Phase 1/3/4, the clean engine, Lohnart computation, or the finalization checks, state the rule you believe you are preserving before editing.
