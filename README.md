## What it is

A multi-tenant SaaS for German taxi and Mietwagen fleets: import the monthly Fahrtenbuch (the XLSX ride log), assign drivers to vehicle blocks, and produce the Stundennachweise and a corrected Fahrtenbuch that reconcile with the Steuerberater's figures. Around that it keeps drivers, vehicles, Belege, salaries, the weekly Abrechnung and the cash till.

A React SPA on a self-hosted Supabase stack (PostgreSQL, Auth, Storage, Edge Functions); there is no application server of our own. The UI is German and English with German as the fallback, and generated documents, domain terms, money and dates stay German (`41,47`, `DD.MM.YYYY`). Since 23.09.2026 every screen is converted: the engines name a dictionary key beside their German text (PR #112) and the last visible labels, buttons and empty states go through `t(...)`.

**What is not fixed, and why.** The payroll arithmetic around Schicht compression and the 30-minute minimum is measured but **blocked on a rule, not on code**: correcting the compression alone would *raise* pay by 4.471,40 €, because the path it is measured against is worse — the 30-minute floor is summed where it should be unioned, worth 11.544,70 € over four months. The questions that settle it are in `Docs/audit/FRAGEN_AN_DEN_STEUERBERATER_2026-09-28.md`, written for the accountant. The remaining plan items live in `Docs/audit/FIX_PLAN_2026-09-28.md`; the one with a date is the DST-blind premium windows, since the next transition is **25.10.2026**.

**In review, outside the phase table: a Rückkehrpflicht tab in the Fahrtenanalyse.** For every imported ride it shows whether the order reached the vehicle during its previous ride, at the Betriebssitz, or away from it after the previous ride had ended, and it lists rides whose own data does not add up: the same address twice, a speed no car drives, an order transmitted after the ride began. It calls nothing a violation, and on purpose: the export records where the vehicle was when an order arrived, never where it was when a ride ended, so a vehicle away from its base may simply have been on its way back. Measured on staging first: 8,455 follow-up orders arrived after the previous ride had ended, against 3,991 during it. The Betriebssitz is the operator's entry, because the data cannot be trusted to reveal it. An administrator saves it for the whole company, and the database refuses a point outside Germany.

**On staging: the monthly plan's second type, a shift recommendation (#188).** `/monatsplan` now opens on two cards; the standard plan behind the first is unchanged to the byte. The second learns, from the imported months, what a vehicle on the road earns per hour by weekday and quarter-hour, and recommends for a coming month when each vehicle should be out: shifts of 3:00 to 4:45, at most two a day with half an hour between them, only where the history beats a threshold the operator sets, and never more vehicles at once than the history ever had out. **It produces no rides.** The brief it answers asked for generated rides — addresses, fares, tips, cancellations, GPS in the Auftragsbuch's own format — calibrated to a target revenue, and that part was declined: a Mietwagen cannot know next month's rides, so such a list is only usable as the record. A test reads the module's source and fails if it ever reaches the database or grows a ride. It has not yet been opened on staging, and its headline figure — fewer hours at a higher rate — was measured on synthetic rides only.

**In review, outside the phase table:** the premium windows were blind to daylight saving. Every band was `localMidnight + N * 3600000` and some day walks stepped `+= 86400000`, so both transition days misclassified an hour, in opposite directions: spring forward over-paid (the 40 % band swallowed an hour owed 25 %) and fall back paid night work inside 00:00-04:00 at **no premium at all** — the band did not hand the hour to 25 %, it slid an hour earlier and dropped it into Grundlohn. The next transition is **25.10.2026**. Sweeping for the shape found four sites rather than the two the fix plan named, and one worse than DST: `FinalizePlanningModal` walked **UTC** days, so its band labelled 00:00-04:00 measured 01:00-05:00 or 02:00-06:00 *every day of the year* and its 23:00 band lay inside its own 00:00-04:00 band, which could pay one minute twice. All 26 Lohnart golden snapshots stay byte-identical — the stated criterion, since none covers a transition day — and the new test reproduces the **old** arithmetic to compare against, agreeing exactly over 365 shifts across 2026 outside the two transitions. Measured on staging's copy of production: 26 trips on 29.03.2026, 75 ride-minutes moving from 40 % to 25 % and 45 from 25 % to Grundlohn, zero on 25.10.2026. It reprints nothing; reissuing a delivered sheet is the owner's separate decision.

**In review, outside the phase table:** the RLS kit could be lied to. PostgreSQL resolves schema `USAGE` when a statement is *parsed* and plpgsql caches the parsed form, so a privilege error inside a `SECURITY INVOKER` trigger is raised only for the first role that cannot parse it — and the permission matrix runs every fixture as the owner before it probes anyone. PR #117's roles trigger reached `app_private`, which no company administrator may use: the feature was dead for every user and the kit passed twice. One `DISCARD PLANS` per principal closes it, a regression section fails if that is reverted, and two catalogue rules in `assertions.sql` stop the shape coming back. What the cache masks is a table rather than a sentence, and it is measured rather than read off the source — a reading of PostgreSQL's internals was wrong three times here, in both directions. Schema `USAGE` is masked; `EXECUTE` is masked only for an inlinable `sql` callee and not for a plpgsql one or one carrying a `SET` clause; table privileges and RLS are not. One thing is measured and **unexplained** — why the matrix's `roles I` cell moved — and it is recorded as open rather than guessed at. The mask is also **not** confined to a test fixture: two ordinary roles on one pooled connection are enough, one holding a privilege and one not. **Production exposure is nil today, measured read-only** — no schema and no inlinable function is granted unevenly across the three roles PostgREST uses in a way anything reaches, and none of them can use `app_private` at all — but it is a standing property, so a migration that grants one of those roles what another lacks reopens it. The two queries to re-run are in CLAUDE.md.

**In review, outside the phase table:** the Excel files were not drawn and they were signed. `xlsx@0.20.3` discards every cell style on write — one font, two fills and one empty border for a whole file — and three exports were still on that writer: Umsätze, Gehälter and Notizen. Each described fills, bold headers and widths and each produced a plain grid, with every figure written as a string by `.toFixed(2)`, so a column of money could not be summed. All three are drawn by the ExcelJS path now, as a set of sheets rather than one stacked dump. The signature went with them, everywhere a file carries one: the footer band naming the system and the row count, the `Author`/`Company` document properties, the writer's fallback creator, the `EL-PROFESSOR - …` title rows, the per-page line in the Belege PDF, and the fallback that headed a company's own summary with our name when its settings were blank. The band survives as an opt-in, because the payroll summary passes a real note there — that the surcharge columns must not be added to the hours — and the first pass of this change deleted it. The gate is a test that writes each workbook through the real `exceljs`, **reads the bytes back**, and fails on a sheet with no fill or border, on a workbook whose every figure is text, or on any cell or property naming the product. What is deliberately still plain: the Fahrtenbuch exports, which must reproduce an imported sheet byte for byte, and the Fahrerübersicht re-import template, whose cell positions must not move.

**In review, outside the phase table:** "Neu verteilen" produced the same plan, and it was right to. The seed reached one decision — the tie-break between candidates whose scores are *exactly* equal — and on a month whose drivers have different salaries no two scores tie, so the button correctly returned the identical distribution and looked broken; the owner reported it three times, and an explanation screen did not answer it. What varies now is the order blocks are offered to the greedy pass, displaced from chronological by a bounded seeded amount, with seed 0 still strictly chronological so a month's first plan does not move. Nothing is relaxed: §7's nine hard rules are asked per (driver, block) pair whatever order the pairs arrive in. And regeneration is a search rather than a gamble — a dozen seeds, each scored on six figures the engine already computes, the best kept, with the plan on screen among the candidates so the answer can never be worse than what it replaces. Measured on a fortnight with three differently paid drivers: eight seeds, eight distinct plans, one identical quality, **24 of 28 blocks moved against a single tie in both plans combined**, which is the control that says the ordering did the work. In the same change a block is no longer shorter than 1.5 hours unless its day gives no choice: a short block is merged into a neighbour of the same vehicle on the same local day, which **merges and never pads**, so `rideMinutes` is unchanged and the absorbed gap shows as idle time. A block with nothing on its day to join stays short and is named on screen rather than hidden.

**Outside the phase table:** the weekly Abrechnung by e-mail, all three parts. Every driver gets an address and a phone number, the Abrechnung can be mailed to one driver from its detail dialog, and one button on the week's Total row mails everyone who has an address. Two parts of three are in: the contact columns — measured first, `drivers` had 33 columns and not one was a contact detail — and the mail transport. The phone is stored as E.164 from the first day because the owner's next step for it is WhatsApp, and `wa.me` takes digits with no plus, no trunk zero and no separators; a number stored as an operator types it could not become a link later without reprocessing thousands of rows. Attachments were new to this product: every mail it sent was `multipart/alternative`, two *alternatives* of one message, and an attachment sits beside the text, so the message becomes `multipart/mixed` with the pair nested inside — **with nothing attached it is byte-for-byte what it was**, which is what keeps the five byte-pinned templates and every OTP mail untouched. The wording is fixed German and pins three things: no figure in the subject, because a subject shows on a lock screen; a negative difference reads *Guthaben* rather than *Abzugeben*, with the sign dropped because the word carries the direction; and it never calls itself a Lohnabrechnung, a Quittung or a Rechnung. The third part is in: `send-document` and the two buttons. **The recipient's address is never taken from the request** — it is read out of `public.drivers` by id, scoped to the caller's own company, so a body naming an address is ignored and one naming another company's driver is refused before anything is rendered; the figures and the image do come from the screen, deliberately, because the mail and the attached card can only agree by coming from one place. "Send to all" is the browser looping one call per driver, so one result per driver reaches the confirmation — sent, no address, or failed — and a name that matches two drivers is **refused rather than guessed at**. The owner decided, asked twice, that staging keeps sending real mail, so the confirmation lists every address before anything goes. **It is proved from the mailbox, not from the screen:** the e2e walk reads Mailpit and found `Abrechnung Woche 3 - November 2026 – DEMO Monatsplanung GmbH` at `emil.normal@example.com` with `Abrechnung_Woche_3_November_2026.png` attached — while the toast on screen reported nothing at all, which is exactly why the assertion is on the mailbox.

## Run it locally

Needs Node.js 24 (`.nvmrc`) and npm.

```bash
npm install
cp .env.example .env   # VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, VITE_APP_URL
npm run dev            # Vite dev server
npm run build          # ratchets, tests, vite build, mail templates
npm run test           # vitest run
```

`VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` point at a Supabase stack — staging's for day-to-day work. `VITE_APP_URL` is the origin baked into auth email links; it may stay blank locally and must be the real domain in production.

End-to-end tests run against staging: `cd e2e && npm install && npm run setup && npm test` ([e2e/README.md](e2e/README.md)). The SQL boundary is checked with the RLS kit, which runs on the VPS ([CLAUDE.md](CLAUDE.md)).
